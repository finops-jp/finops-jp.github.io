**概要:** FinOps実践者（FinOps Practitioner）は、エンジニアリング（Engineering）チームと協力し、クラウドの請求データとKubernetesのメトリクス、ワークロードのメタデータ（Metadata）を組み合わせることで、コンテナコストを算出・配賦（Allocation）できます。ネームスペース、チーム、サービスにわたるコスト配分（Cost Allocation）を改善することで、組織はコンテナ化されたアプリケーションの実行にかかる真のコストをより正確に把握できます。本稿では、透明性の高いコンテナコストレポートを作成し、データ駆動型の最適化（Optimization）に関する意思決定を支援するための基本概念と実践的なアプローチを説明します。

### はじめに

読者は、クラウドコンピューティングの仕組みに関する基本、主要なクラウドプロバイダーのサービスと一般的なユースケース、および請求と価格モデルの基本を理解している必要があります。また、クラウド運用の基本的な価値提案を説明でき、従量課金制（pay-as-you-go）の利用モデルという核心的な概念を理解していることも求められます。

さらに、3大パブリッククラウドプロバイダー（AWS、Azure、Google Cloud）のうち、少なくとも1つに関する基礎知識が必要です。AWSについては、AWS Business Professionalトレーニング、またはAWS Cloud Practitioner認定の取得を推奨します。Google Cloudについては、Google Cloud Platform Fundamentalsコースを確認してください。Azureについては、Azure Fundamentalsのラーニングパスをお試しください。いずれも通常、1日のワークショップで完了できます。

## コンテナコスト配分の課題

多くのチームでコンテナやコンテナオーケストレーター（Container Orchestrator）の採用が進む中、これらのコンテナ化されたワークロードがFinOpsプラクティスに与える根本的な影響を理解することは極めて重要です。コンテナのような共有リソースは、コスト配分、コストの可視性、リソース最適化において課題を生み出します。

コンテナ化された環境では、従来型のFinOpsコスト配分（リソースのコストをチームやプロジェクトに1対1でマッピングする手法など）は機能しません。リソース上で複数のコンテナが実行され、それぞれが異なるアプリケーションをサポートしている場合があるため、リソースのコストを単一のタグやラベルに単純に配分することはできません。また、それらのコンテナが組織内の異なるコストセンター（Cost Center）に紐づいている場合もあります。

すでにFinOpsプラクティスを確立しているチームであっても、これからこの専門分野を構築しようとしているチームであっても、クラウドの利用コストをその要因に1対1でマッピングする難しさには誰もが共感するはずです。そこにコンテナとKubernetesが登場します。突如として、これまでの基本的なクラウド財務管理プラクティスに微調整が必要になります。しかし、心配は不要です。同じFinOps原則（FinOps Principles）とプラクティスを適用することで、チームはコンテナ化の支出を正確に追跡できます。

本ホワイトペーパーは、FinOpsチームがクラウドでのコンテナ化に取り組む前に理解しておくべき重要な疑問、課題、考慮事項を網羅するために作成されました。すでにコンテナ化されたサービスを利用している場合は、本ガイドを活用して、チームが強力かつ最新のFinOpsベストプラクティスに基づいて運用できているかを再確認してください。

本ホワイトペーパーでは、一般的なコンテナの用語と概念を説明します。また、FinOpsのコアプラクティスの観点から、Kubernetesとコンテナのコストを調査し、対処します。

  * **把握（Inform）:** パブリッククラウドプロバイダーがKubernetesサービスに対してどのように課金するかを理解する。Kubernetes環境においてチャージバック（Chargeback）やコスト配分を行うことがなぜ難しいのかを学ぶ。
  * **最適化（Optimize）:** Kubernetesクラスターとポッド（Pod）を継続的に最適化する方法を模索する。
  * **運用（Operate）:** コンテナコスト配分へのアプローチを決定し、コンテナ支出を管理するポリシーを構築する。また、従来のクラウド支出と並行してコンテナコストを管理するためのツールを統合する。

## FinOpsの視点から見るKubernetesコスト

コンテナ化がFinOpsにもたらす課題（コストの可視性、コストのショーバック（Showback）/チャージバック、コスト最適化）に目を向けると、これらはクラウド移行時に直面した困難とまったく同じであることにすぐに気づきます。

コンテナは、クラウド仮想化の上にあるもう一つの仮想化レイヤーであり、コスト追跡において新たな複雑さを生み出します。これらの課題を解決するために、基本的なFinOpsプラクティスを適用します。

本稿では、コンテナとKubernetesにおけるFinOpsの課題を、広範なクラウドFinOpsに適用するのと同じ**把握（Inform）、最適化（Optimize）、運用（Operate）**のライフサイクルに当てはめて解説します。

### 関連する用語と概念

詳細に進む前に、コンテナやKubernetesに馴染みのない方のために、基本を素早くおさらいします。また、本ホワイトペーパー全体を通じて、これらのコンポーネントに関する共通認識を形成する上でも役立ちます。

_**注意:** AWS Elastic Container Service（ECS）とKubernetesには多くの共通点がありますが、それぞれで使用される用語は異なります。本書では、Kubernetesについて具体的に言及する場合を除き、簡潔にするため、Kubernetesの「ポッド」と「ノード（Node）」をそれぞれ「コンテナ」と「サーバーインスタンス」と表現します。_

コンテナとは、極めてシンプルに言えば、ソフトウェアをパッケージ化する手法です。すべての要件と設定が、デプロイ可能なイメージ（Image）に組み込まれます。Kubernetesのようなコンテナオーケストレーションツールは、エンジニアが管理可能かつ保守可能な方法でサーバーにコンテナをデプロイするのを支援します。

本章を通じて使用するいくつかの重要な用語は以下の通りです。

| **用語** | **定義** |
|---|---|
| イメージ（Image） | 実行に必要なソフトウェアを含むコンテナのテンプレート。 |
| コンテナ（Container） | コンテナイメージのインスタンス。同じイメージの複数のコピーを同時に実行可能。 |
| サーバーインスタンス/ノード（Server instance/node） | クラウドサーバー（EC2インスタンス、仮想マシンなど）。 |
| ポッド（Pod） | Kubernetesの概念。ポッドはコンテナのグループで構成され、クラスター上でスケジューリングやスケーリングが可能な単一のリソースブロックとして扱われる。 |
| コンテナオーケストレーション（Container orchestration） | サーバーインスタンスのクラスターを管理し、コンテナ/ポッドのライフサイクルを維持する仕組み。コンテナオーケストレーターの一部であるスケジューラーが、サーバーインスタンス上で実行するコンテナ/ポッドをスケジューリングする。例としてKubernetesやAWS ECSがある。 |
| クラスター（Cluster） | コンテナオーケストレーションによって管理されるサーバーインスタンスのグループ。 |
| ネームスペース（Namespace） | Kubernetesの概念。他のネームスペースから分離してポッド/コンテナをデプロイできる仮想クラスター。 |
| ポッドラベル（Pod labels） | ユーザーにとって意味があり関連性のあるオブジェクトの属性を識別するためのキー/値（Key/Value）のペア。コアシステムに直接的な意味は与えない。各オブジェクトに一連のキー/値ラベルを定義でき、キーはオブジェクト内で一意である必要がある。複数のネームスペースをグループ化したい場合などに役立つ。 |

## Inform: How Container and Kubernetes Costs Are Generated

最初の焦点は、チームが運用しているクラスター上の個々のコンテナコストを特定するレポートを作成することです。これは、コンテナ支出の可視性を構築するための基礎的なステップとなります。

### コントロールコスト配分の違い

クラウドサービスプロバイダーは、クラスターを構成するすべてのサーバーインスタンスに対してチームに課金します。コンテナがクラスターにデプロイされると、クラスターのリソース容量を消費するため、これらの料金が発生します。プロセスが実行された瞬間に料金が発生します。これは、クラウドサービスプロバイダーでサーバーをプロビジョニングする場合と同様です。そのサーバーリソースを使用しているかどうかにかかわらず、料金を支払います。

クラスター上で実行される個々のコンテナコストを配分するには、個々のコンテナが基盤となるサーバーをどれだけ消費したかを特定する方法が必要です。また、稼働中のクラスターに付随する周辺コスト（Satellite Costs）も理解する必要があります。これには、管理ノード、クラスターの状態を追跡するために使用されるデータストア、ソフトウェアライセンス、バックアップ、および潜在的な災害復旧（DR）コストが含まれます。これらのコストはすべてクラスターの運用に伴うものであり、コスト配分戦略において考慮する必要があります。

### コストの複雑さをもたらすコンテナの機能

ユーザーがコンテナオーケストレーションサービスを好む理由は、以下の事項を大幅に簡素化できる点にあります。

  * 利用要件に基づいてチームがコンテナを起動するスケジューリング
  * さまざまな粒度でのネットワークスケーリングと接続の管理
  * 変化するワークロードに適応するための、ノード作成および削除のオートスケーリングと自動化

主要なすべてのクラウドプロバイダーが提供する仮想マシン（VM）サービス上でKubernetesを実行することも、Kubernetesクラスターを管理するネイティブサービスを利用することもできます。例として以下があります。

  * AWS：Amazon Elastic Kubernetes Service（Amazon EKS）
  * Google Cloud：Google Kubernetes Engine（GKE）
  * Microsoft Azure：Azure Kubernetes Service（AKS）
  * IBM Cloud：IBM Cloud Kubernetes Service
  * Oracle Cloud Infrastructure：Oracle Container Engine for Kubernetes
  * Alibaba Cloud：Container Service for Kubernetes（ACK）

各プロバイダーは、チームのクラウド移行支援を含め、独自のレベルのサポートとサービスを提供しています。これらのサービスはすべて、他のクラウドサービスと同様に従量課金制です。従量課金制のクラウド請求は便利ですが、1つのクラスターで複数のチームによる複数のプロジェクトを実行できるため、クラウド財務管理とコスト配分が課題となります。

マネージドKubernetesサービスに対する従来の請求アプローチは、クラスターごとの時間料金に加えて、クラスターが消費する追加の基盤リソースに対して課金するものです。これにより、クラウドの請求書を見るだけではコンテナクラスターによってどのリソースが消費されているかを単純に判別できないため、コンテナコスト管理が特に困難になります。

### Kubernetesコストの請求とレポート作成が難しい理由

コンテナ環境でのコスト配分は、従来のクラウド環境よりも多くの課題をもたらします。従来のクラウド環境では、FinOps実践者はコンテナ以外のリソースを1対1でタグ付けできるため、レポートツールを使用してサービスをコストセンターに簡単にマッピングできます。これらのアプリケーションに対する責任の割り当ては、アプリケーションベンダーのタグをチームにマッピングするだけの作業です。

Kubernetesでは、タグとチームの1対1のマッピングだけでは、コンテナ利用によって生じる複雑なユースケースの一部をカバーできません。ほとんどのKubernetesクラスターは、任意の数のチームがアプリケーションを実行する共有サービスです。つまり、特定のコンテナに直接的なコストが発生するわけではなく、一連のコンテナが組み合わさって、ワークロードのクラスターごとにコストが発生します。クラウド料金を特定のコンテナ使用量にマッピングする簡単な方法はありません。

コンテナはKubernetesクラスターにデプロイされ、他のテナントと同様にクラウドリソース（コンピューティングなど）を消費します。課題は、各クラスター内で、通常は複数のチームがそれらの基盤リソースの一部を消費している点にあります。

さらに、コンテナ化された環境は非コンテナ環境よりもはるかに動的であり、VMの利用時間が通常はるかに長いのに対し、[コンテナの平均寿命は1日](https://www.google.com/url?q=https://www.datadoghq.com/container-report/&sa=D&ust=1606873149474000&usg=AOvVaw31ESoO5kTZWVAy7WoBpCQA)です。Kubernetesスケジューラーの動的な性質を考慮すると、ワークロードはインスタンスタイプ、ゾーン、あるいはリージョンをまたいで再スケジュールされる可能性があります。このため、急速な変化のペースに追従しなければならず、コスト管理はさらに複雑になります。

### コンテナ支出を管理するコスト配分プラクティスとポリシーの例

**クラウド財務管理において、予測可能性は最も重要です。** 経験豊富なFinOps実践者は、コストを予算内に抑え、想定外の事態を最小限に抑えます。データセンターのコストに慣れているチームは、コストが固定かつ定期的であることを知っています。クラウドサービスへの移行はこの前提を変え、コンテナ化は状況をさらに複雑にします。

### Kubernetesにおけるコンテナのクラス

Kubernetesのようなクラスターオーケストレーションソリューションでは、スケジュールされたコンテナに対して、Quality of Service（QoS）クラスと呼ばれる異なるリソース保証を設定できます。

#### 帯域保証型（Guaranteed）リソース割り当て

重要なサービスのコンテナには、帯域保証型リソース割り当てを使用して、設定された量のvCPUとメモリが常にポッドで利用可能であることを保証できます。帯域保証型リソース割り当ては、予約された容量と考えることができます。コンテナのサイズと形状は変化しません。

#### バースト型（Burstable）リソース割り当て

スパイクの発生するワークロードは、必要なときにだけ多くのリソースにアクセスできるメリットを享受できます。基盤となるサーバーインスタンスの容量に余裕がある場合、ポッドは最初に要求した量以上のリソースを使用できます。バースト型リソース割り当ては、一部のクラウドサービスプロバイダーが提供するバースト可能なサーバーインスタンス（AWSのTシリーズやGCPのf1シリーズなど）に似ており、基本レベルのパフォーマンスを提供しつつ、必要に応じてポッドがバーストできるようにします。

#### ベストエフォート型（Best effort）リソース割り当て

さらに、開発/テスト用のコンテナはベストエフォート型リソース割り当てを使用できます。これにより、余剰容量がある間はポッドを実行し、容量がなくなると停止します。このクラスは、GCPのプリエンプティブルVM（Preemptible VM）やAWSのスポットインスタンス（Spot Instance）に似ています。

コンテナオーケストレーターが、異なるリソース割り当て保証を持つポッドを各サーバーインスタンスに混在させて割り当てると、サーバーインスタンスの利用率が向上します。固定リソースのポッドに基本量のリソースを割り当て、サーバーリソースの残りを上限として使用する可能性のあるいくつかのバースト型ポッドと、利用可能になった予備容量を使い切るためのいくつかのベストエフォート型ポッドを配置できます。

基本事項を説明しましたので、本セクションの次のパートでは、コンテナコスト配分を開始するためのいくつかの戦術を探ります。以下について説明します。

  * 開発、運用、財務の間の理解を深め、より予測可能な予算に向けて取り組む。ツールを使用してヒューマンエラーを自動的に排除し、クラウド財務の正確性を高めてコンテナ化サービスを利用する。
  * リソースまたはアプリケーション定義の集約を使用する。個々のチームが多数の独自のプロジェクトを作成するのを防ぎ、代わりに定義された専用のクラスターを使用する。
  * チームをネームスペースに割り当てることで、それぞれのプロジェクトやチームにコンテナコストを正確にチャージバックする手段を提供する。
  * コンテナクラスターのラベルを使用して、クラウドサービスのタグ付け（Tagging）を次のレベルに引き上げる。

### 具体的なコンテナ化コストの詳細な分析

Google CloudのBilling Product ManagerであるDebo Aderibigbe氏が推奨する1つの手法は、コストを以下のように分解することです。

  * **請求階層（Billing Hierarchy）:** 組織、フォルダ、プロジェクト。これらをクロスプラットフォームの概念（リンクされたアカウント、タグ、サブスクリプションなど）で標準化する。
  * **リソース（Resources）:** コンピューティングコア、RAM、GPU、TPU、ロードバランサー、永続ディスク、カスタムマシン、ネットワーク送信（Egress）。
  * **ネームスペース（Namespaces）:** 特定の隔離されたコンテナのラベル付け。
  * **ラベル（Labels）:** チーム、コストセンター、アプリケーション名、環境など。

これらすべてのコスト要因に対して詳細なラベル付けとタグ付けを行うことで、ユーザーはチームへの請求、コスト監査、コスト配分、超過コストの最適化、予算シナリオのモデリング、またはクォータ内や予算上限内へのワークロードコストの収容の精度を向上できます。

### LiveRamp社におけるGKE上のコンテナ化コストへの取り組み

LiveRampチームは、オンプレミスのサービスをGoogle Cloud Platformに移行し、コンテナサービス（およびコスト）をスケールアップさせましたが、これが財務チームの目に留まりました。技術的な移行は成功したものの、1ヶ月後に予算が超過してしまいました。彼らは何が起きたのかを説明する方法を必要としていました。

当時、LiveRampにはFinOpsへの文化的なシフトが欠けており、開発者はクラウド財務に対する自分たちの新しい責任を理解していませんでした。この理解を深めるため、コンテナに焦点を当てたFinOps原則が、クラウドコストと運用の意思決定を異なる方法で合理化するのに役立ちました。彼らは、すべてのチームが独自のアカウントとセットアップを持っていることから生じる課題を克服しなければなりませんでした。

FinOpsに焦点を当てた多大な取り組みの結果、大規模クラスターに対するネームスペースの強制適用や、配分の精度を向上させるためのより優れたタグ付けとラベル付けなど、FinOpsの重要なプラクティスである新しいポリシーが組み込まれました。また、Cloudability、CloudHealth、ネイティブツールなど、クラウド財務管理におけるチームのニーズに適したツールを見つけることも役立ちます。

### 配分を改善するための整合性のあるラベル付けとネームスペース戦略

一貫性があり堅牢なラベル付けとネームスペース戦略を実装したら、クラスターコストをどのように配分するかを検討し始めることができます。GKEを使用している場合を除き、クラスター内でどのグループがコストを発生させているかを簡単に確認することはできません。

一般的な方法論は、各グループ（ラベル、ネームスペースなど）が消費したリソースの割合を確認し、それを使用してクラスターコストをそれらのグループに配分することです。たとえば、クラスター内に4つのネームスペースがあり、それぞれがクラスターリソースの25%を消費している場合、クラスターの総コストの25%をそれぞれのネームスペースに配分することを決定できます。

現実の世界では、どのような環境であってもこれほど単純でわかりやすいものはありません。複雑さを増すもう一つの要因は、クラスターのリソース利用率をどのように決定するかという点です。CPU、メモリ、あるいはその両方の組み合わせに基づいて決定するのでしょうか。リソース要求（Requests）と実際の消費量（Consumption）のどちらを考慮したいでしょうか。

これらのアプローチのメリットとデメリットは、以下の表の通りです。

| | **リソース要求（Resource Requests）** | **実際の使用量（Actual Usage）** |
|---|---|---|
| **メリット** | ・すべてのコストを配分できる<br>・チームに必要な分だけをプロビジョニングするよう促せる<br>・支援ツールが存在する（Vertical Pod Autoscalerなど） | ・各チーム/アプリケーションは使用した分だけを支払う |
| **課題** | ・一部の組織では、リソース要求フィールドをまだ使用していない<br>・要件を過小に指定する動機を与える可能性がある | ・残りのコスト（アイドル時間/サイクル）は誰が支払うのか？<br>・過剰プロビジョニングにどう対処するか？<br>・念のために多くプロビジョニングし、支払いを避けるようチームを動機付ける可能性がある<br>・利用率100%という非現実的な目標を設定してしまう可能性がある |

### コアクラスターコストの先へ

クラスターの利用者にコストを配分する際は、コンテナが動作したコンピューティングノードのコストだけでなく、クラスターの運用に伴う周辺コストも考慮することが重要です。

#### 管理/クラスター運用コスト

クラウドサービスプロバイダーから請求されるクラスター管理コストや、自主管理型のコンテナオーケストレーターノードの実行によって発生するコストを考慮する必要があります。WAFやロードバランサーなどのエッジサービスも、クラスター上でワークロードを実行する全体的なコストに影響します。

#### ストレージコスト

コンテナ内のサービスによってストレージがエフェメラル（一時的）として扱われる場合でも、コンテナはストレージを消費します。コンテナの外部においては、ノード上のホストOSや、本番クラスターの運用で使用されるバックアップまたはデータ取得用ストレージを考慮し、これらをクラスター上で実行されているワークロードに配分できます。

#### ライセンス

ホストノードでライセンスが必要なオペレーティングシステムを実行している場合、ライセンスコストは常に興味深いトピックです。ライセンスコストは、クラウドサービスプロバイダーによる請求に含まれている場合があります。しかし、ライセンス持ち込み（BYOL）を使用してこれらを運用している場合、ライセンスコストは外部支出から配分する必要があります。ホストオペレーティングシステムに加えて、ライセンス料が発生するホストOS上のソフトウェアパッケージも考慮してください。コンテナ内で実行されているワークロード自体も、配分が必要なライセンスソフトウェアを使用している場合があります。

#### オブザーバビリティ（可視化）

多くの場合、メトリクスやログはクラスターから、チームが可視化、監視、アラート通知を行えるサービスに送信されます。このデータは、クラウドサービスプロバイダーが提供するサービス、またはサードパーティのSaaSソリューション（Splunk Cloud、Sumo Logic、Datadog、SignalFxなど）に送信されます。

#### セキュリティ

主要なクラウドサービスプロバイダーは現在、安全なクラウド環境の維持を支援する非常に広範なセキュリティ関連サービスを提供しています。しかし、これらのセキュリティ機能を有効にすることは多くの場合無料ではなく、これらの追加コストをチームに配分する必要がある場合があります。

上記のすべてのソースから発生する1ドル単位のコストをコスト配分戦略に含めたくなるかもしれませんが、すべてのFinOpsと同様に、まずはシンプルに始めて、時間をかけてプラクティスを成長させること（クロール（Crawl）、ウォーク（Walk）、ラン（Run））を推奨します。これらのコスト配分項目を一度にすべて実装しようとすると圧倒されてしまう可能性があります。コストを配分するプロセスと、組織内での配分に対する理解の両方を構築していくことで、段階的に攻略するアプローチ（Divide and Conquer）の方が成功する可能性が高くなります。

### 静的コストと実行時コンテナコストへの対処

コンテナ化コストは、主に静的コスト（Static Costs）と実行時コスト（Runtime Costs）の2つのタイプに分けられます。

#### 静的コスト

静的コストについては、プロジェクトに対するソリューションの品質を確保するためにコンテナ内にソリューションを作成することだけでなく、デプロイ時にそれがCPU、ネットワーク、ストレージにどのように影響するかを考慮する必要があります。静的コンテナコストは、ステートレス（Stateless）コンテナとステートフル（Stateful）コンテナにさらに分類できます。ステートレスの例は以下の通りです。

  * 静的リソースを持つWebサーバー：Apache、Nginx、IIS
  * アプリケーションサーバー、ステートレスアプリケーション：Tomcat、nodeJS、JBoss、Symphony、.NET
  * マイクロサービス：Spring Boot、Play、Quarkus
  * ツール：Maven、Gradle、スクリプト、テスト

#### ステートフルアプリケーションを持つアプリケーションサーバー

アプリケーション内でユーザーセッションを保存する必要性がしばしば生じます。このケースに対処する2つのアプローチは、セッションアフィニティ（Session Affinity）を持つロードバランサーを使用してユーザーが常に同じコンテナインスタンスにアクセスするようにするか、すべてのコンテナインスタンスが共有する外部セッション永続化メカニズムを使用することです。

ポータルや永続化レイヤーのキャッシュなど、ネイティブなクラスタリングを提供するコンポーネントもあります。通常は、ネイティブソフトウェアにインスタンス間の同期と状態の管理を任せるのが最善です。インスタンスを同じオーバーレイネットワーク上に配置することで、高速かつ安全な方法で相互に通信できるようになります。

#### データベース

データベースは通常、ファイルシステム上にデータを永続化する必要があります。ベストプラクティスは、データベースエンジンのみをコンテナ化し、そのデータはコンテナホスト自体に保持することです。これは、ホストボリュームを使用して実行できます。例：`$ docker run -dit -v /var/myapp/data:/var/lib/postgresql/data postgres`

Kubernetesは、マネージドデータベースサービスの代替としても使用できます。たとえば、MongoDBやElasticsearch専用のクラスターを使用することで、わずかなコストでフルマネージドサービスに近いものを提供できます。

#### 共有ファイルシステムを持つアプリケーション

コンテンツ管理システム（CMS）は、PDF、画像、Wordファイルなどのドキュメントを保存するためにファイルシステムを使用します。これもホストボリュームを使用して実行でき、多くの場合、複数のCMSインスタンスが同時にファイルにアクセスできるように共有ファイルシステムにマウントされます。

#### 実行時コスト

実行時コストは、多くの人にとってコンテナでは静的なものと想定されています。コンテナをどのように実行するかは、最終的な収支に影響します。クラウドサービスプロバイダーから発生するこれらのコストの例は以下の通りです。

  * 帯域幅（Bandwidth）は、クラウドコンピューティング料金の見積もりにおいて見落とされたり、過小評価されたりしがちです。
  * デプロイしたまま忘れてしまったコンテナ化アプリケーションは、想定外の請求を招く確実な原因となります。アプリケーションやデータをクラウドに配置すると、それらを削除するまで、毎月コストが発生し続けます。クラウドに何かを配置してそのまま忘れてしまうことは非常に簡単です。
  * コンピューティング料金は実際の使用量（CPU利用率など）に基づいていません。
  * クラウドでのデータポーリング（Polling）はコストのかかるアクティビティであり、トランザクション手数料が発生します。ポーリングの量によっては、コストがすぐに膨らむ可能性があります。
  * DoS攻撃やスパイダーなどによる意図しないトラフィックは、予期しない方法でトラフィックを増加させる可能性があります。このような意図しない料金に対処する最善の方法は、アプリケーションのセキュリティを監査し、CAPTCHAなどの制御手段を提供することです。
  * 管理：アプリケーションの健全性と請求状況を定期的に監視する。クラウド上にあるものが本当にまだ必要かどうかを定期的に見直す。アプリケーションの負荷量を定期的に監視する。負荷に合わせてデプロイのサイズを調整する。

### 本番環境におけるコンテナコスト削減の考慮事項

コンテナ化されたデプロイは、ステートレスでフォールトトレラント（耐障害性）なアプリケーションを実行する場合、オンデマンド価格と比較して最大90%の割引を実現できます。エフェメラルかつステートレスであるべきコンテナは、正常な起動（Graceful Startup）と正常なシャットダウン（Graceful Shutdown）を遵守します。

これらの特性により、実行時にのみ課金されるサーバーレス（Serverless）デプロイはより魅力的になります。別の捉え方をすれば、休止状態の間は料金が発生しません。ただし、パフォーマンスを伴う同等の機能を得る必要があるため、コンテンツをサーバーレスAPIにデプロイするだけでは不十分です。コールドスタート（Cold Start）が最大の敵となります。

しかし、Apache Beamなど、クラウドプロバイダー上でユニバーサルなバッチサーバーレスロードを実行できるようにする新たな領域が開かれつつあります。これが有効になると、多様なクラウドプロバイダーのエンジン（ランナー）にわたる実行を可能にする高度なデータ並列処理パイプラインに従うことで、ITの多くの新しい領域がコスト削減に参加できるようになります。

## Optimize: Build in cost Efficiencies for Kubernetes

把握フェーズと同様に、コンテナの世界における最適化フェーズは、クラウドプラットフォーム向けに構築された独自のFinOpsプラクティスを直接適応させたものですが、コンテナの複雑さを考慮して適用されます。

コンテナ化によってライトサイジング（Rightsizing）の問題が解決されるという議論もあります。同じサーバーインスタンス上でより多くのワークロードを実行する方が、コスト効率が高く見えるためです。しかし、これまで見てきたように、どのチームやプロジェクトがこれらのコストを発生させているのか、あるいはクラスターから実際に節約効果を得られているのかを測定することは複雑なタスクです。

成功を収めるために、FinOpsプラクティスをどのように進化させる必要があるかを見ていきます。

Kubernetesコストのチャージバックに成功したら、次のステップは、コストを削減するためにKubernetes環境を最適化する方法を模索することです。Kubernetesコストが制御不能に急増するのを防ぐために、FinOps実践者がDevOpsチームと連携して実施できるいくつかのステップがあります。

### ポッド/コンテナのライトサイジング

コンテナが適切な量のリソースを要求していることを確認します。要求が少なすぎるとアプリケーションが動作できなくなるため、通常、コンテナに設定された要求（Requests）または制限（Limits）と、実際に必要な量との間にはある程度のバッファが存在します。

このバッファが必要以上に大きい場合が、コスト削減の機会となります。Vertical Pod Autoscaler（VPA）は、コンテナの使用実績に基づいて要求と制限の設定を自動的に調整し、オーバーヘッドを削減しながらリソースとコストを節約するのを支援するオープンソースプロジェクトの一例です。

Horizontal Pod Autoscaler（HPA）は、ワークロードに対してスケールアップ/ダウン（垂直スケーリング）ではなく、スケールアウト/イン（水平スケーリング）を行うためのものです。ここでの注意点は、VPAとHPAのポリシーが互いに干渉しないようにすることです。

ビニング（Binning）とパッキング密度（Packing Density）の設定は重要であり、目的別またはビジネスクラスのサービス層向けにクラスターを設計する際に見直す必要があります。開発用やコスト重視のクラスターでは、ホストあたりにできるだけ多くのコンテナを配置することを目指します。一方で、本番環境やパフォーマンス重視のクラスターの設定では、異なるニーズやパターンに合わせてスコープが定義されます。アプリケーションのインスタンスファミリーごとに適切な量のポッドとネームスペースを一致させる能力を持つことは、適切な容量、可用性、オーバーヘッド、および経済性を確保する参照モデルを構築するための優れた方法です。

もう一つの注意点は、コンテナへの適切なトラフィックシェーピング（Traffic Shaping）と負荷管理を確保するために、Ingressコントローラーの設定が活用されているか確認することです。

### ノードのライトサイジング

次は、クラスターのワーカーノード（Worker Node）タイプの選択です。これは、さまざまなプラットフォームの選択肢に伴うあらゆる複雑さを除けば、一種のビンパッキング問題（Bin Packing Problem）となります。

ノードに常に過剰なメモリがあることに気づいた場合など、単に段階的な改善を行うだけで、同じタイプでメモリが少し少ないノードタイプに切り替えることが合理的になる場合がよくあります。しかし、実際にはこれはより複雑になる可能性があります。たとえば、要求した量よりも多く消費することが多いワークロードがある場合、それが本当に必要だったケースと、単に利用可能だったから消費されただけで極めて重要ではなかったケースを区別する必要があります。

実行に適したインスタンスサイズ/タイプのホワイトリストを作成する際は、インスタンスの重み付け（Instance Weighting）スコアの使用を検討してください。インスタンスの重み付けは、価格が同じである可能性のあるスポット市場で多様な割り当て戦略に依存している場合に有用であり、重み値に基づいてコードに適した価値がプロビジョニングされるようにするのに役立ちます。

### オートスケーリングの調整

Kubernetesを特に強力にしているのは、豊富なオートスケーリングオプションと、需要の増減などの異なる状況に動的に対応できる能力です。これをアプリケーションに合わせて適切に設定するには、ある程度のアーキテクチャ設計と反復的な調整が必要であり、その過程で無駄が生じる余地があります。しかし、水平ポッドオートスケーリング（ポッドの増減が必要なとき）とクラスターオートスケーリング（ノードの増減が必要なとき）が緊密に設定されているほど、アプリケーションの実行に伴う無駄や不要なコストは少なくなります。

#### 割引タイプ

ほとんどのクラウド環境では、条件がユーザーとアプリケーションに合致する限り、大幅な節約を可能にする割引オプションが提供されています。

#### スポット/低優先度/プリエンプティブルワーカーノード

これらはプロバイダーによって名称が異なりますが、通常、短時間での予告により消失する可能性のあるワークロードに対して割引を提供します。これにより、クラウドプロバイダーはすべての容量の空きを埋めるインセンティブを提供しつつ、オンデマンド料金を支払う優先度の高いワークロードの流入に対応できます。

Kubernetesの宣言的な性質により、ワーカーノード群の割り込みが検知されて置き換えられるため、スポット割引を活用しやすくなります。それでも、一部のアプリケーションはこれらの割り込みを許容できない場合があります。このプロファイルに該当する可能性のあるアプリケーションには、バッチで実行されるデータ集中的なワークロードや、機械学習のトレーニングなど、時間的な制約がそれほど厳しくないワークロードが含まれます。

#### コミットメント割引

これらもリザーブドインスタンス（Reserved Instance）、Savings Plans、コミットドユース割引（Committed Use Discount）、サブスクリプション割引など、いくつかの名称やメカズムがありますが、いずれも通常、クラウドプロバイダーへの長期的な支出コミットメント（Commitment）と引き換えにユーザーに割引を提供します。これらは一般的にコンピューティングリソースをカバーしており、特定のクラウド（場合によっては特定のワークロードタイプ）で1年以上の継続的な利用を見込んでいるユーザーにとって、クラスターコストを削減するための選択肢となります。

購入方法の組み合わせ（Purchase Method Mix）を有効にし、オンデマンド、コミットメント、スポットの変動価格の分割割合を宣言する機能は、それをコスト効率のブループリントに自動化するための優れた方法です。

例：コントロールプレーンには10%のコミットドユース、非本番環境のワーカー/レプリカには90%のスポット、本番環境には50/50の割合など。

事前に構築されたHelmチャートや起動計画を作成し、さまざまな最適化をすべて含めて再利用できるように公開することで、最小限の経験と摩擦でその知見を実践に移すことができます。

「Kubeless」や「サーバーレスコンテナ」は、クラウドプロバイダーがより高次のサービスを提供して消費される新たな選択肢であり、顧客におけるKubernetesクラスターの運用および管理のスキル不足を解決できる可能性があります。また、FPGAタイプのインスタンス上でKubelessソリューションを検討する動きもあり、これにより結果が劇的に高速化し、コストが大幅に削減され、OSやKubernetesクラスターのログ記録、パッチ適用、監視、保守に必要なOSやコンテナのオーバーヘッドを排除できます。

* * *

### クラウドコストの視点：大規模マルチクラウド企業におけるコンテナ利用の複雑さを解き明かす

コンテナ化とクラスターコストをある程度制御できていると思った矢先に、企業の合併や買収（M&A）が発生し、別のクラウドサービスプロバイダーが1つか2つ追加されることがあります。これにより、企業が完全なチャージバックとコスト配分を実施する方法が複雑化する可能性があります。

ネイティブツールであれ専用アプリケーションであれ、クラウドコスト管理プラットフォームを導入することで、コンテナコスト配分の複雑さと摩擦を軽減できます。クラウドコスト管理プラットフォームは、以下の基本がカバーされている場合に最も効果的です。

  * Kubernetesの構成要素ごとに利用率を観察し、それをクラウドの請求データに関連付ける。
  * Kubernetesのラベルのキー/値ペアを使用して、内部のコストセンターと整合させる。
  * Kubernetesのラベルキーと従来のキータグを統一し、配分モデルを深化させる。

これらの基本が整っていれば、企業のインフラストラクチャがどれほど複雑であっても、FinOpsチームはKubernetesコストを包括的な方法で説明できます。クラスターやネームスペースごと、あるいはコストセンターごとにコストを分析し、これらのコストを完全に、かつ正確に正しく配分できます。

_— Casey Doran氏（Apptio Cloudability プロダクトディレクター）_

## Operate: Build Policies and Practices to Manage Kubernetes Costs

Kubernetesコストを正確に配分できるようになり、それらのコストを最適化する方法がわかったら、次はFinOpsに焦点を当てたポリシーと取り組みを強制するための持続可能なプラクティスを構築する番です。たとえば、開発用コンテナを営業時間に合わせてオン/オフするようにスケジュールすること、アイドル状態のコンテナを検出して削除すること、強制適用によってコンテナのラベル/タグを維持することなどは、チームに教育し、活用を促すべきプラクティスの一部にすぎません。

### クラウドコストの視点：強固な基盤からFinOpsチームをスタートさせる

コンテナ化コストをより適切に追跡するためのプラクティスやポリシーを追加する前に、チームが強固なクラウド財務管理の基礎を備えていることを確認してください。財務チームやクラウドコストのCoE（Center of Excellence）全体と協力して整合を図り、以下の質問に対して明確な回答を用意します。

  * インフラストラクチャ全体で確立されたレポート機能とKPIがありますか。
  * チームは、クラウド財務ガバナンスとポリシーが遵守されていることを確認するためのチェックを継続的に実行していますか（ネームスペースの使用方法の理解、タグのないリソースへのタグ付け、プロジェクト/チームに関連付けるためのセマンティックタグの使用、エラーを減らすためのタグ修正の自動化など）。
  * チームは必要な分だけをプロビジョニングできていますか。それらのコストが何に基づいているかを説明し、正確にレポートできますか。
  * 共有の共通サービスのコストは誰が支払いますか。
  * チームは、クラウドリソース利用を最適化する機会を積極的かつ頻繁に特定していますか（また、そうするための権限が与えられていますか）。

これらの質問に答えるには、まずFinOpsの重要なベストプラクティスを実装する必要があるため、まずはそれらを確認してください。また、チームが同じ利用率とコストのレポート確認し、効率向上のために協力して行動できるように、クラウドコスト管理ソリューションが必要になる場合もあります。

_（提供：Jonathan Morin氏、CloudHealth by VMware シニアプロダクトマネージャー）_

### コンテナコストを管理するツールの選択肢

コンテナコストを含むクラウドサービスのFinOps習得を目指す企業の多くは、通常、3つの経路のいずれかを選択します。内製ツールを構築してDIYで成功を目指すか、クラウドサービスプロバイダーが提供するネイティブツールを使用するか、あるいは専用のクラウド財務管理プラットフォームを使用するか、すべての選択肢にメリットとデメリットがあります。

#### DIYによるコンテナコストの追跡

チームにそのための人材とリソースがある場合、コンテナコストを含むクラウド財務データを追跡するDIYアプローチを作成することは、この支出を理解する手段になり得ます。Spotify社など、大規模な企業が現在これを実施しており、[backstage.io](https://backstage.io)を介して独自のクラウド管理ツール群を運用しています。

これは、チームがクラウド利用の初期段階にあり、この方法で管理できる程度の請求データを生成している場合にも合理的です。

#### ネイティブツールを使用したコスト追跡

社内ツールと併用してネイティブツールを使用することも、FinOpsを成功に導くもう一つの経路です。クラウドコストデータにアクセスして消化し、ビジネスに適合するチャージバックとレポートを生成する手段がある限り、良好な状態を維持できるでしょう。ただし、チームがマルチクラウドインフラストラクチャを運用している場合は、各プラットフォームが提供するそれぞれのツールを使用する必要があります。

また、これらすべてのクロスプラットフォームの財務データを1つのビューに集約するために、別のデータ可視化または分析ツールが必要になる場合もあります。

#### クラウド財務管理プラットフォームの使用

特定の規模に達すると、手動での取り組みはメリットよりも苦痛をもたらすようになり、ネイティブツールや専用のクラウド財務管理プラットフォームを使用する時期が来ます。これにより、手動によるヒューマンエラーが排除され、（すべてが正確にタグ付けされ命名されていることを前提として）配分作業をツールに任せることができます。

これにより、共有のKubernetesクラスターとそのコストに対する可視性が向上します。また、チームやプロジェクトごとにコストを配分する方法も改善できます。クラウド財務管理プラットフォームは、多くの場合、マルチクラウドの請求データもサポートする機能を備えています。

ただし、FinOpsプラクティスの大部分は、サードパーティツールが提供する機能セットや価格設定に縛られることになります。また、クラウドインフラストラクチャの規模に見合った公正な取引を得るために、価格設定、契約、交渉について毎年ビジネス上の合理性を判断しなければならない場合もあります。まずは、FinOps Foundationの「FinOps認定プラットフォーム（FinOps Certified Platforms）」を確認することをお勧めします。

### 開発者がKubernetesの利用率を追跡できるように権限を与え、動機付ける

インフラストラクチャが適切にタグ付けおよびラベル付けされていれば、開発チームとFinOpsチームのメンバーが利用データを追跡するための独自のカスタムレポートを構築する基盤が整います。ネイティブツールのAPIやクラウド財務管理ツールを利用するかどうかにかかわらず、チームが独自の監視環境を作成して管理できるように権限を与えることは、非常に役立ちます。

開発者は、サービスの稼働時間やパフォーマンスをリアルタイムで監視するのに役立つ主要なインフラストラクチャメトリクスをすでに追跡している可能性が高いでしょう。これらの既存のメトリクスにコストデータを追加することで、大きなワークフローの変更を伴わずに、この情報を意思決定プロセスに組み込むことができます。

> 「このデータと並んでコストを第一級市民（First-class citizen）として取り込むことは、エンジニアがインフラストラクチャやアプリケーションレベルの変更による影響を簡単に測定できるようにする、高度なFinOpsの取り組みです。」 — Webb Brown氏（Kubecost社 CEO）

支出と利用率を追跡するコストだけでなく、既存のワークフローの一部となっているツールを活用することで、開発者がKubernetesのセットアップをさらに効率化できるように支援します。多くの場合、これはコンテナに焦点を当てたオープンソースツールを採用することを意味します。Helmのようなアプリケーション管理ツール、Prometheusのような監視ソリューション、Argoのようなコンテナワークフローエンジン、Linkerdのようなサービスメッシュソリューションは、エンジニアリングチームがほぼリアルタイムでKubernetesクラスターの実用的な可視性を得るのに大いに役立ちます。

## FinOpsによるKubernetesコスト管理課題の解決

FinOps実践者は、クラウドが今後さらに複雑になる一方であることを知っており、強力なクラウド財務管理プラクティスを持つことで、コストのレポート作成や配分が容易になることを理解しています。

本ホワイトペーパーでは、チームがコンテナコストをレポートする際の精度を向上させ始めるための、いくつかの強力な基礎的ステップを概説しました。本書では以下を網羅しました。

  * **把握（Inform）:** パブリッククラウドプロバイダーがKubernetesサービスに対してどのように課金するか。Kubernetes環境においてチャージバックやコスト配分を行うことがなぜ難しいのかをレビューしました。
  * **最適化（Optimize）:** Kubernetesクラスターとポッドを継続的に最適化する方法を模索する方法、およびテストすべきいくつかの戦術を推奨しました。
  * **運用（Operate）:** コンテナコスト配分へのいくつかのアプローチを概説し、コンテナ支出を管理するポリシーを構築する方法、および従来のクラウド支出と並行してコンテナコストを管理するツールを統合する方法を説明しました。また、チームがクラウド財務ポリシー、追跡、ガバナンスを構築するのに役立つさまざまなタイプのツールをレビューしました。

よりユーザーがコンテナとKubernetesを採用して稼働させるにつれて、利用データと財務データの両方を追跡することに関する新しいベストプラクティスが形成されています。これは、コンテナに対する私たちのFinOpsの視点が常に変化し、進化していることを意味します。
