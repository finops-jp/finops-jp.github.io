**概要：** ハードウェア、ファシリティ、人件費などの複雑なデータセンター支出を、パブリッククラウド環境で使用される予測可能なユニットベースの言語に変換するための、構造化されたフレームワークとアプローチを習得します。データセンターのレートカード（Rate card）を作成する方法と、既存のクラウドやSaaSのレポートとシームレスに統合し、FOCUSに準拠したコストレコードを生成する再現可能なマッピングプロセスを学びます。これにより、データセンターを効率的に運用する関係者や経営陣に対して情報を提供するための、クリーンで拡張性の高いレポート作成の基盤を構築できます。

## データセンターにFinOpsを適用する理由

組織は、パブリッククラウド環境に求めるものと同等の正確性と透明性を持って、データセンターで実行するワークロードのコストを理解し、伝達できることをますます期待しています。データセンターのコストと使用量の可視性は、クラウド、SaaS、ライセンスに使用する意思決定支援フレームワークと同じものに統合する必要があります。明確な社内価格設定とFOCUSに整合したデータセットにより、単なるコスト管理にとどまらず、CIO、CTO、CFOレベルでの価値、成長、長期的な投資計画に関する議論が可能になります。

組織がFinOpsプラクティスを成熟させるにつれて、データセンターのコスト可視化の役割は運用レポートの枠を超え、[経営幹部レベルの意思決定](<https://www.finops.org/insights/finops-enabled-executive-decisions/>)を同様に支援するようになります。明確な社内価格設定、一貫したユニットエコノミクス、およびFOCUSに整合したデータセットは、経営陣が依存するシナリオモデリング、投資評価、および戦略的なワークロード配置の意思決定を可能にします。クラウドやSaaSで使用されるものと同じ構造化され比較可能な言語でデータセンターのコストを表現することで、FinOpsチームはテクノロジーの選択をビジネス成果に結びつけ、戦略計画を加速させる組織の能力を強化します。

現代のテクノロジーリーダーは、コンピューティングやストレージといったデータセンターの構成要素から、AIのような複雑なテクノロジースタックに至るまで、組織のテクノロジー投資を一元的に把握することをますます求めています。データセンターを含む構造化されたコストモデルは、FinOpsエグゼクティブ（FinOps Executive）に対して、オンプレミスとクラウドの経済性を同じ言語で比較する能力を提供し、ワークロード配置、モダナイゼーション、および長期的なキャパシティ計画に関する戦略的な意思決定を可能にします。

データセンターのコストと使用量をテクノロジー意思決定支援フレームワーク全体に組み込むには、2つの重要な要素があります。

  1. **資産コスト：** データセンターサービスの価格設定とチャージバックを可能にし、組織の財務要件を満たすのに必要な程度まで、データセンターの基礎となる資産とコストを十分に詳細に理解すること。
  2. **サービスのチャージバック：** 組織内のエンジニアリングチームやプロダクトチームに提供するデータセンターサービスが、どのように提供、価格設定、および消費されるかを定義すること。

すべての組織において、これら2つのプロセスのいずれも最も細かいレベルの詳細さで実行する必要はありません。すべてのデータセンターのコストと価格を定義するための鍵となる単一のタクソノミ（Taxonomy）は存在しません。[FinOpsリーダー](<https://www.finops.org/framework/persona/leadership/>)の役割は、利用可能な情報が下すべき意思決定をサポートするのに十分なレベルに達している時期を組織が理解できるように支援することに最も適しています。特定の組織における社内外の財務報告の具体的な要件によって、規制、報告、コンプライアンス、またはその他のニーズを満たすために、コストとチャージバックのマッピングをどの程度詳細かつ包括的に行う必要があるかが決まります。

本稿では、財務理論やアーキテクチャの詳細よりも、シンプルさ、一貫性、および運用上の使いやすさに焦点を当てたアプローチを重視します。歴史的に、多くのチャージバックの取り組みが失敗したのは、技術的な制限によるものではなく、電気代やファシリティ予算などのコストを再配分することが組織の境界を越えて政治的および財務的な緊張を生み出したためです。

## 基本概念

### クラウドと比較したデータセンターの経済性

パブリッククラウドのコストのみに焦点を当ててきたFinOpsチームの視点から見ると、データセンターの経済性を理解することは、次の2つの根本的な事実を認識することから始まります。

  * 第一に、**データセンターのコストの大部分は、その中で実際にどれだけのワークロードが実行されているかに関係なく発生する**こと。
  * 第二に、**データセンター内部の使用量測定**は、パブリッククラウドプロバイダーが公開しているものほど均一でも詳細でもないことが多いこと。

これ以降のすべて（コストモデル、レートカード、配賦方法、およびFOCUSデータセット）は、組織がこれら2つの現実にどれだけうまく対処できるかにかかっています。

### データセンターのコスト特性

**データセンターは、固定費または準固定費が大部分を占めます。** データセンターの運営は、ホテルの運営によく似ています。資金の大部分は、宿泊客が現れる前に消費されます。建物を建て、客室を整備し、ホテルの環境を魅力的に保つためのシステムを構成します。これらのコストは、ホテルが満室であっても、半分であっても、あるいは空室であっても、ほとんど変わりません。

データセンターも同様に機能します。ハードウェアは事前に購入されて数年にわたって減価償却され、電力供給、冷却設備、フリーアクセスフロア、ネットワーク室などのファシリティコストは、サーバーが稼働中かアイドル状態（Idle）かに関わらず発生します。仮想化、監視、自動化ツールなどのプラットフォームソフトウェアには、時間ごとの使用量によって変動しない予測可能なサブスクリプションやサポートのコストがかかります。

これらのコストは、利用率に関係なく回収しなければならないベースラインを形成します。ワークロードが静かであるか統合されている場合でも、電力供給は利用可能でなければならず、冷却は室内の環境を維持しなければならず、ハードウェアは良好な動作状態に維持されなければなりません。クラウド環境では、この複雑さはプロバイダーの価格設定の背後に隠されていますが、データセンターでは、組織がこれを所有し、理解し、コストモデルに組み込む必要があります。

CPUやGPUの利用率によって変化する電力消費や、実際のトラフィックに応じてスケールする帯域幅などの変動要素は存在しますが、これらは通常、全体の支出のごく一部にすぎません。変動部分が実際にはいかに小さいかを理解せずに、組織が使用量ベースの価格設定を作成しようとすると、結果として得られるモデルは不正確または不整合に感じられることがよくあります。この間違いを避けるためには、データセンターの大部分を占める固定コストベースを明確に理解することが極めて重要です。

### データセンターにおける使用量とテレメトリの測定

基礎となる要素は、ワークロードがデータセンターのリソースをどのように消費しているかを示すデータの使いやすさです。ほとんどの組織は、仮想化レイヤーから基本的な測定値を収集できます。これには、経時的なvCPU時間、メモリコミットメント、ストレージ容量、および何らかの形式のネットワークスループットが含まれます。これらのメトリクスは、表現および比較可能なコストの単位を作成するために不可欠です。

**しかし、データセンターのテレメトリ（Telemetry）が均一であることは滅多にありません。** 一部のクラスターは豊富な利用率レポートを提供しますが、他のクラスターは粗いサマリーしか公開しません。ネットワーク機器はテナントごとのトラフィックデータを提供しない場合があり、ファシリティシステムはラックごとやホストごとではなく、部屋レベルでしか電力や冷却を測定しない場合があります。タグ付けのプラクティスも一貫していない可能性があり、リソースの背後にあるチームやプロダクトを確実に特定することを困難にします。

これは、不揃いな地図のコレクションを使ってナビゲートするようなものです。あるセクションはすべての路地や裏通りを示す都市地図のような精度で描かれ、別のセクションは島の輪郭しか見えない古い海図のようにスケッチされています。同じデータセンター内を移動しているにもかかわらず、詳細レベルが場所によって急激に変化するため、実際に測定、属性特定、および信頼できる内容が制限されます。

また、データセンターのテレメトリがクラウドのテレメトリよりも本質的に劣っているわけではないことを認識することも重要です。多くの環境において、SNMP、ハイパーバイザーのカウンター、スイッチやルーターの統計情報、および配電テレメトリを通じて収集されるシグナルは、ホスト利用率、ネットワークスループット、および電力関連のプロキシ（Proxy）の正確で監査可能な測定値を提供します。クラウドプロバイダーも同様の基礎となるメカニズムに依存していますが、それらをより標準化された消費APIを通じて表面化させています。

FinOpsにとって重要なのは、テレメトリがオンプレミスとクラウドのどちらから発生しているかではなく、それらの測定値がvCPU時間、GB月、または帯域幅などの価格設定単位にどのように変換されるかです。一貫した測定間隔と属性特定方法が確立されれば、これらの変換は簡単に行えます。

データの欠落はコストモデルの作成を妨げるものではありませんが、モデルをどの程度詳細にできるか、またコスト要素からチャージバック価格へのマッピングをどの程度正確に作成できるかに大きく影響します。クラウド環境でもテレメトリの欠落や不整合が発生するため、どちらの環境でも、使いやすい消費モデルを構築するには解釈と簡素化が必要です。

使用量の測定が不完全または不均一な場合、コストモデルはブレンド（Blending）または簡素化によって補う必要があります。不完全なテレメトリの上に非常に細かい課金メカニズムを構築しようとすると、ほぼ確実に不満と不信感につながります。より現実的なアプローチは、確実に測定できるものを認め、その能力に合わせてレートモデルを形成することです。

プロバイダーが一般的により標準化されプログラム可能なレート情報を提供するパブリッククラウドとは対照的に、データセンターは機器レベルの購入データや、ハードウェア、ファシリティ、ライセンス、人員配置などの基本コストから始まります。社内レートはこれらのインプットから集計する必要があります。オンプレミス環境はネイティブな使用量ベースの価格設定を提供しないため、社内レートはこれらのインプットから集計する必要があります。クラウドは基礎となるインフラストラクチャの経済性を隠しますが、データセンターでは、FinOpsがそれらを構築しなければなりません。

これらの基本概念を理解した上で、次の課題は設計です。コストモデルは、データセンター支出の固定的な性質と、社内テレメトリの不均一な品質を考慮する必要があります。そこから、組織はインプットコスト、測定精度、および使いやすいレートカードを作成するために適用するブレンドの量のバランスを見出すことができます。

### コストインプット、メトリクス精度、およびレートブレンドのバランス調整

使いやすいデータセンターのコストモデルを作成することは、単にすべての請求書を収集したり、インフラストラクチャが公開しているすべてのメトリクスを抽出したりすることではありません。モデルが成功するのは、組織が支出、測定可能な内容、およびキャパシティを消費するチームに対してコストをどれだけシンプルに提示したいかの間で、適切なバランスを見出したときだけです。これら3つの次元（インプットコスト、使用量測定、およびブレンド戦略）が、アプローチ全体の実用性と信頼性を形成します。

#### 第一：組織が表現することを選択するコスト詳細の度合い

一部のチームは、サーバー、ストレージ、電力のみという狭い視野から始めます。他のチームは、プラットフォームソフトウェア、ライセンス、ファシリティ、運用人件費、および共有テクノロジーサービスを含む、より広い視野を持ちます。詳細を増やすことで正確性は向上しますが、モデルに組み込む必要のある要素の数も増加します。早い段階で詳細にしすぎると、コストに関する議論が明確になるどころか、かえって困難になる可能性があります。

#### 第二：利用可能な使用量メトリクスの精度と完全性

環境が信頼性の高いvCPU時間測定値、ストレージ利用率、および所有権メタデータ（Metadata）を提供する場合は、コストを消費に密接に結び付けることができます。しかし、特定のプラットフォームが限られたテレメトリしか公開していない場合、過度な詳細さを求めると誤解を招く結果が生じます。消費モデルは、理論上の理想ではなく、一貫して測定できる内容に基づいている必要があります。

#### 第三：レートカード作成時に適用されるブレンドの量

ブレンドとは、データセンター支出の複数の構成要素を、たとえば「vCPU時間あたり0.022ドル」のような単一の安定した社内レートに組み合わせる手法です。非常に詳細なモデルでは、コンピューティング、ファシリティ、ソフトウェアライセンス、および運用の料金を個別に維持する場合があります。よりブレンドされたモデルでは、これらのインプットを、エンジニアリングチームが理解しやすく使いやすい、より少数のシンプルなレートにまとめます。レートカードがブレンドされるほど直感的になりますが、各構成要素が単独で可視化される割合は低くなります。

#### すべてを組み合わせる

これら3つの要素（インプットコスト、測定精度、およびブレンド）は、個別にではなく、一緒に管理する必要があります。テレメトリの制限を考慮せずに正確性を重視した設計は、信頼性の低い結果を生み出します。シンプルさだけに焦点を当てたモデルは、重要な支出要因を覆い隠してしまう可能性があります。 And a model that attempts to reflect every nuance of data center spending can become too complicated for practical use.

ほとんどの組織は、最終的に中間的な立場を選択します。

  * データセンター運用の現実を反映するのに十分なコスト詳細
  * コストと使用量を信頼できる方法で整合させるのに十分な測定精度
  * エンジニアリングチームが自信を持って計画を立てられる、明確で予測可能なレートカードを作成するのに十分なブレンド

重要な点として、データセンターのコストモデルを構築するこの初期段階において、目的は会計レベルの照合や財務的な完全性ではありません。目標は、使いやすいモデルを作成することです。つまり、チームが自分たちのワークロードが何を消費しているか、その消費が財務的に何を意味しているか、および自分たちの意思決定が共有データセンターのキャパシティに与える需要にどのように影響するかを理解するのに役立つモデルです。優先すべきは、完璧さよりも、明確さ、予測可能性、および共通の理解です。

この取り組みの一環として、組織はどのコスト要素をレートカードにブレンドし、どれを個別に処理するかを意図的に決定する必要があります。ファシリティオーバーヘッド、電力や水の管理、人員配置などの一部の費用は、中央予算に残り、既存の総勘定元帳（GL：General Ledger）プロセスを通じて回収される場合があります。このような状況では、これらのコストが社内レートの範囲外にあることを組織が理解している限り、エンジニアリングチームから見えない状態のままであっても問題ありません。

その他のコストは、使用量ベースの料金ではなく、固定、一回限り、または定期的な項目として、チームに直接表示または請求される場合があります。重要なのは、これらの境界が意図的かつ透明であり、時間の経過とともにより詳細で洗練されたものに発展できるモデルをサポートしていることです。

インプット、測定、およびブレンドのバランスを理解した上で、次のタスクは、これらのコンポーネントをエンジニアリングチームが信頼できる構造化されたデータセンターコストモデルに組み立てることです。

### コストモデルからレートカードへ

データセンターのレートカードの構築は、エンジニアリングチームが依存するサービスを提供するためにどれだけのコストがかかるかを明確に理解することから始まります。データセンターの費用は通常、予算、契約、ファシリティ、および運用チームに分散しているため、最初のタスクはその複雑さに構造をもたらすことです。目標は、完璧な財務的精度を達成することではありません。代わりに、明確で、正当性を主張でき、日々の意思決定に役立つモデルを確立することを優先します。プラクティスが成熟するにつれて、より高い正確性と照合を進めることができます。

プロセスは、データセンターの運営に必要な主要なコンポーネント（ハードウェア、ファシリティ、プラットフォームソフトウェア、運用人員、およびサポートサービス）を特定することから始まります。用語は組織によって異なりますが、意図は一貫しています。これらのインプットは、キャパシティを利用可能にするための本質的なコストを表しています。

**調達サイクルも、これらの基礎となるコストを形成します。** 多くの組織は、ハードウェア、ソフトウェア、またはコロケーション（Colocation）契約を定期的に再交渉しており、これらの合意の変更はデータセンターのコストベースを実質的に変化させる可能性があります。契約更新によって価格が低下すると、それらの削減は組織の損益計算書に直接反映されるため、調達のタイミングや交渉結果は、レート設定や財務計画における重要な考慮事項となります。更新された契約条件を予測可能なケイデンスでモデルに組み込むことで、社内レートが過去の前提ではなく、組織の現在の商業的立場を反映していることを確実にできます。

#### サービスへのコストマッピングとレートカードの構築

これらのインプットを理解したら、それらをデータセンターが提供するサービスに関連付けることができます。ほとんどの環境では、共有クラスター、専用ホスト、GPUノード、複数のストレージ階層など、さまざまなコンピューティングおよびストレージサービスが提供されています。これらのサービスの一部はエンジニアリングチームによって直接消費されますが、他のサービスは環境をより広く支えています。目的は、テレメトリがサポートできないレベルの精度を要求することなく、資金がどこに費やされているかと、それらの投資が可能にするサービスとの間に論理的な接続を確立することです。

このサービスマップを確立した後、組織は各サービスをレートカードにどのように表示するかを決定する必要があります。これには、異なるコスト要素をどの程度ブレンドするか、そして何を個別に提示するかを選択することが含まれます。多くのチームは、基本コンピューティングレートにファシリティ、ライセンス、および運用人件費を含めることを選択し、これにより価格設定をシンプルかつ安定に保ちます。

高性能ストレージや特殊なネットワーキングなどの他のサービスは、チームがそれらのコストの具体的な要因を理解し、影響を与えることができるように、個別に維持されることがよくあります。重要なのは、これらの選択が意図的であり、エンジニアリングチームが消費するサービスについてどのように考えているかと一致していることです。

#### 戦略的シグナルとしての社内価格設定

社内価格設定はコストを反映するだけでなく、シグナルでもあります。一部の組織では、リーダーシップが戦略的な行動（クラウド移行の加速、データセンター利用率の向上、不足しているオンプレミスキャパシティを過剰消費するワークロードの回避など）を促すために、純粋なコストモデルよりわずかに高い、または低い社内レートを意図的に設定する場合があります。これらの調整は透明性を持って適用されるべきです。

意図的なインセンティブを組み込んだレートカードは、ワークロード配置を導くための強力なツールになり得ますが、明確な根拠なしに行われると、モデルに対する信頼を損なうリスクがあります。重要なのは、基礎となる経済性からの乖離が意図的であり、オープンに伝達され、長期的なアーキテクチャおよび財務戦略と一致していることです。

利用率やテレメトリが不完全であり、多くの費用が消費に応じてスケールしないため、コストのブレンドはしばしば必要になります。減価償却、冷却、プラットフォームソフトウェア、および運用を組み込んだコンピューティングレートは、不要な詳細でチームを圧倒することなく、安定した財務シグナルを提供します。同時に、真にオプションのサービスや階層化されたサービスを分離することは、エンジニアリングチームがパフォーマンスとコストについて情報に基づいた選択を行うのに役立ちます。

#### 社内レートの計算とガバナンス

構造が定義されたら、組織は社内価格を計算します。選択したレートカードレベルの粒度で一貫して測定できないコスト要素については、通常、各サービスを提供する年間コストを推定し、その金額を予想される消費の現実的なレベルで割る必要があります。

利用率の前提も重要な要因です。完璧な利用率に基づくレートは人為的に低い価格を生み出し、短期的な変動に結びついたレートは頻繁に変動しすぎて信頼できません。ほとんどのチームは、共有コンピューティング、ストレージ、およびネットワーク帯域幅に関する過去のデータセンター利用率に基づいて、安定した利用率ターゲットを採用しています。これにより、公平で予測可能、かつ計画に適した価格が作成されるためです。

資産が老朽化するにつれて、その減価償却または償却スケジュールにより、通常、同じレベルのキャパシティを提供する実効コストが低下します。財務的に成熟した組織は、次の2つの方法のいずれかでこれを可視化します。

一部の組織は、時間の経過に伴う資本回収要件の低下を反映した、ガバナンスに則り定期的に見直される「レート引き下げポリシー」を適用します。他の組織は、この影響をレポート内で「償却メリット（Amortization benefit）」または同様の行として明示的に表面化させ、レートカードの価格設定に急激または予測不可能な変化をもたらすことなく、レガシー資産がどのようにコスト軽減に寄与しているかをチームが理解できるようにします。どちらのアプローチも、財務的な経年変化が透明性を持って認識され、提供コストの正当な削減が実務者に可視化されることを確実にするのに役立ちます。

資産コホート（Cohort）が減価償却スケジュールの終了に達すると、その残存資本コスト要件はゼロになります。運営費（OPEX）が比較的低いサービスの場合、これにより実効提供コストがOPEXのみのレベルに近づき、資産のライフサイクルの初期に使用されていたレートを大幅に下回ることがあります。

組織は、この影響をどのように表面化させるかにおいて異なります。安定性のために一定の管理されたレートを維持する組織もあれば、減価償却後のコスト軽減を透明性を持って反映させ、チームが低コストのキャパシティを活用できるようにする組織もあります。この挙動を可視化することは、効率的なワークロード配置と、古い資産のより効果的な利用を促進できます。パブリッククラウドプロバイダーも同様の原則を大規模に適用しています。たとえば、サーバー群の耐用年数を延長することで、資本コストがゼロのハードウェア期間から利益を得て、マージンを改善しています。

設計全体を通じて、透明性は依然として不可欠です。複数のコスト要素がブレンドされている場合でも、エンジニアリングチームは各レートに何が含まれており、それがなぜなのかを理解する必要があります。「このコンピューティングレートには、ハードウェアの減価償却、ファシリティ、プラットフォームライセンス、および運用人件費が含まれています」といった簡潔な説明は、信頼を築き、データセンターが不透明な社内コストではなくサービスとして運営されているという考えを強化します。組織はいつでも、時間の経過とともにより細かく、またはより詳細にする計画を立てることができます。

レートカードには意図的なガバナンスが必要です。消費の短期的な変化や運用上のノイズに応じて価格を変動させるべきではありません。頻繁な調整は計画を台なしにし、モデルに対する信頼を低下させるためです。実用的な出発点は、何がなぜ変更されたかについての明確なコミュニケーションを伴い、たとえば毎年または年に2回といった予測可能なサイクルでレートを見直し、更新することです。

#### 効果的な変更管理によるレート変更の実施

新規または更新された社内レートの導入は、組織が明確さと予測可能性を持って変更を管理するときにのみ成功します。チームは、何が変更されるかだけでなく、なぜ調整が行われるのか、およびそれが長期的な効率性、キャパシティ計画、または財務的な整合をどのようにサポートするのかについて、事前通知を必要とします。早期かつ一貫して共有される明確なメッセージングは、不確実性を軽減し、レート設定プロセスに対する信頼を構築するのに役立ちます。

効果的な実施は、プロアクティブなコミュニケーションから始まります。[財務、プロダクトエンジニアリングリーダー、およびFinOps実践者](<https://www.finops.org/framework/personas/>)などの主要なパートナーには、コストの変動、利用率の傾向、戦略的目標など、変更の背後にあるビジネスドライバーが十分に理解されるよう、早い段階で説明を行う必要があります。シンプルな1ページのサマリーやFAQは、疑問が生じた際にステークホルダーにとって安定した参照ポイントを提供できます。

その後、構造化されたエンゲージメント計画により、アップデートがスムーズに適用されるようになります。数週間前に提供されるエグゼクティブプレビューが背景を設定し、ロールアウトが近づいた時点でのチームレベルの説明会は、エンジニアリングおよびプロダクトグループが予測、予算、およびショーバックレポートにどのような影響が及ぶかを理解するのに役立ちます。Slackのアナウンス、オフィスアワー、技術フォーラム、直接の働きかけなど、複数のコミュニケーションチャネルにより、チームは最も信頼しているフォーマットで情報を受け取ることができます。

最後に、ロールアウトには明確なタイムライン、予想される影響範囲、および定義されたサポートパスを含める必要があります。モデリングの支援、最適化のガイダンス、またはワークロードの推奨事項を提供することで、チームは自信を持って更新されたレートに適応できます。意図的に処理されることで、変更管理はレートの更新を突然の驚きから、信頼と運用の成熟度を強化する予測可能で透明なプロセスへと変えます。

これらの変更管理プラクティスは、レートの設定および維持方法に関するより広範なガバナンスを補完するものですが、それとは別のものです。

レートカードがこのように管理および更新されると、単なる価格設定メカニズム以上のものになります。それは、エンジニアリングの一貫した計画、財務の構造化されたコスト意識、およびシニアリーダーが投資決定を導くために使用できる安定したユニットエコノミクスをサポートする共通言語になります。また、プラットフォームチームに対して、提供するキャパシティの価値と経済性を実証する明確な方法を提供します。

レートカードが整備され、サービスが明確な単位で表現されると、組織は利用率とアイドルキャパシティをレポートにどのように反映させるか、およびこれらのシグナルがより広範なFinOpsおよびFOCUSデータパイプラインにどのように流れるかを検討する準備が整います。

### 利用率とアイドルキャパシティの処理

データセンターの決定的な特徴の1つは、キャパシティが消費される前に存在していなければならないことです。サーバー、ストレージアレイ、ネットワーク機器、電力および冷却インフラストラクチャはすべて、ワークロードがそれらを満たすかなり前に取得され、稼働を開始します。これにより、意図的か偶発的かに関わらず、すべてのデータセンターが一定レベルのアイドルキャパシティを抱えるという、避けられない現実が生じます。組織がこのアイドルキャパシティをどのように処理するかは、社内価格設定モデルの成功に大きな影響を与えます。

エンジニアリングチームは利用率を技術的なメトリクスと見なしがちですが、データセンターにおいては経済的なメトリクスでもあります。利用率が高い場合、固定されたデータセンター支出のより大きな割合が、実際のワークロードの稼働に使用されています。利用率が低下すると、その同じ支出がより少数の消費者に分散されるため、各vCPU時間やストレージのGBを提供する実質的なコストが高くなります。

データセンターで一連の機器を稼働させるコストは月ごとに大きく変化しませんが、そのコストから組織が受け取る価値の量は、キャパシティが実際にどれだけ使用されているかによって変化します。

このため、レートカードは短期的な利用率レベルに直接反応することを避ける必要があります。クラスターがビジーまたはアイドルになるたびにvCPU時間の価格が変動すると、エンジニアリングチームはモデルに対する信頼を失い、予算計画に苦労することになります。チームが必要としているのは一貫性です。つまり、運用のノイズに敏感に反応することなく、現実的な利用率レベルを反映した安定した社内価格です。

ここで、アイドルキャパシティの概念が重要になります。利用率の変動によってレートカードが乱されるのを許すのではなく、組織はアイドルキャパシティをデータセンターにおける独自の識別可能なコスト構成要素として扱います。未使用のキャパシティを利用可能な状態に維持するコストは依然として存在しますが、エンジニアリングチームがアクティブに消費するコストとは別に表現されます。これにより明確な分離が生まれます。レートカードは安定したままであり、理論上の利用率と実際の利用率の乖離は、明確で透明な支出カテゴリとして表示されます。

この分離を表現する現代的な方法は、分割コスト配分（Split cost allocation）によるものです。このアプローチでは、組織は安定した利用率の前提に基づいてレートカードを計算します。実際の消費がそのレベルに達しない場合、その差額はアイドルコストまたは未配賦コストとして記録されます。消費されたキャパシティのコストはある行に表示され、アイドルキャパシティのコストは別の行に表示されます。これらを合わせると、データセンターの運営に費やされた総額に等しくなり、効率性インデックスの計算に使用できます。FinOpsポリシーは、この効率性インデックスを使用して、アイドルキャパシティが計画範囲を超えた時期を特定し、是正措置をトリガーする必要があります。

高いアイドルコストは、通常、早期のハードウェア購入、予想を下回るワークロードの成長、または実現しなかった不測の事態に備えて予備として保持されていたキャパシティなどが原因で、データセンターが必要以上の予備キャパシティを抱えていることを示します。もう一方の極端な例として、アイドルコストが非常に低い、またはほぼゼロであることは、必ずしも効率性の兆候ではありません。多くの環境において、これはデータセンターが限界に非常に近い状態で運営されており、新しいワークロード、ハードウェア障害、またはメンテナンスのためのバッファがほとんどないことを示す場合があります。また、廃止措置の遅れ、アグレッシブな統合、または運用リスクをもたらすオーバーコミットメント（Overcommitment）戦略を示唆している可能性もあります。

一部の環境では、クラウドの「スポット」インスタンスやプリエンプティブル（Preemptible）インスタンスと概念が類似した、予備キャパシティ向けの割引社内レートを試験的に導入する組織もあります。これらの大幅に割引されたアイドルレート階層は、日和見的なワークロードを促進することで利用率の向上に役立ちますが、重要なトレードオフも導入します。

割引されたアイドルキャパシティは、中断可能または低優先度として明確に識別される必要があり、チームはこの価格設定が環境を運営する真の持続可能なコストではなく、条件付きの可用性を反映していることを理解する必要があります。使用する場合、これらのメカニズムは、長期的な計画や投資決定に情報を提供する基礎となるアイドルキャシグナルを覆い隠すのではなく、補完するものであるべきです。

アイドルコストの配分方法に対処する前に、健全なアイドルキャパシティがどのようなものかを理解することが有用です。組織は、過剰でも危険なほど低くもなく、計画の前提に整合し、ミッションクリティカルな本番環境に必要な予備キャパシティを管理するポリシーに準拠した、安定した範囲のアイドルキャパシティを目指すべきです。健全で予想されるレベルのアイドルキャパシティは、消費とキャパシティ計画が意図した通りに連携していることを示唆しています。これは、データセンターが不要なオーバーヘッドを抱えることなく、成長や運用の変動を吸収するのに十分な余地を持っていることを意味します。このバランスを長期的に監視することは、プラットフォームチームとエンジニアリングのステークホルダーの両方にとって価値のあるシグナルになります。

アイドルコストへの対処は個別の決定であり、会計構造よりも組織の文化を反映します。未使用のキャパシティは共有の戦略的投資であると認識し、中央のインフラストラクチャまたはプラットフォーム予算に配賦するチームもあります。他のチームは、すべての消費者に比例して配分し、チーム間でコストを効果的に平準化します。可視性を利用して改善を促すために、配賦を一切行わずに単にレポートするだけのチームもあります。

アプローチに関係なく、原則は同じです。**アイドルキャパシティは認識され、意図的に処理されなければなりません。** レートカードの内部にそれを隠すことは、消費の価格を歪め、重要な運用シグナルを覆い隠します。明確に公開することは、より優れたキャパシティ計画、より鋭い予測、およびデータセンターの使われ方に関するチーム間のより建設的な議論をサポートします。

利用率を価格設定への変動インプットではなく計画の前提として扱うことで、組織はデータセンターの完全な経済性を反映しつつ、安定して予測可能なレートを維持できます。これにより、次のステップである、これらのコストと使用量の測定値をFOCUS仕様などの一貫したポータブルな形式で表現し、チーム全体での透明性のあるレポート作成とショーバックを可能にする準備が整います。

利用率が価格設定から個別に処理されることで、組織はこれらの消費および価格設定シグナルを、エンジニアリングチームが使用できるレポートに変換できます。

### レートカード計算の簡略化された例

**シナリオ：** オンプレミスのデータセンタークラスターにおける、1ヶ月あたりのvCPUあたりのコストを決定したいとします。

**含めるべきコンポーネント：**

  * 機器のCAPEX（資本支出）償却
  * 電力と冷却
  * ライセンスとメンテナンス
  * 運用オーバーヘッド
  * アイドルキャパシティ（未使用のvCPU）
  * 使用済みキャパシティ（使用済みのvCPU）

#### ステップ1：クラスターインプットの定義

**ハードウェア**

  * ホスト数：10
  * ホストあたりのvCPU：64
  * 利用可能な総vCPU：640 vCPU

**利用率**

  * 割り当てられたピークvCPU：480 vCPU
  * アイドルキャパシティ：640 - 480 vCPU = 160 vCPU
  * アイドル率 = 25% アイドル

#### ステップ2：月次コスト構成要素

**CAPEX**

サーバー（5年で減価償却、月額コスト）：180,000ドル

**OPEX**

  * 電力：40,000ドル
  * 冷却：32,000ドル
  * VMwareライセンス：60,000ドル
  * ハードウェアサポート契約：20,000ドル
  * platformエンジニアリングスタッフ：25,000ドル

クラスターの月次総コスト：357,000ドル

#### ステップ3：アイドルキャパシティを含めたvCPUあたりのコスト

**計算式**

  * vCPUあたりのコスト = クラスターの総コスト / 総vCPU
  * 357,000ドル / 640 = vCPUあたり558ドル

これは、無駄を含めた「真の」ユニットコストです。

#### ステップ4：利用されたキャパシティのみを使用したvCPUあたりのコスト

**計算式**

  * vCPUあたりのコスト = クラスターの総コスト / 使用済みvCPU
  * 357,000ドル / 480 = vCPUあたり744ドル

これは、アイドルキャパシティによって膨らんだコストを表しています。

#### ステップ5：アイドルキャパシティのコスト影響

  * アイドルキャパシティコスト = 総コスト × アイドル率
  * アイドル率 = 25%
  * アイドルコスト = 357,000ドル × 25% = 89,250ドル
  * CPUあたりの無駄：744ドル - 558ドル = vCPUあたり156ドル

これは、FinOpsのショーバックで使用できる「無駄バケット（Waste bucket）」を表しています。上述した組織のアプローチに応じて、これを無駄を示すメトリクスとして表示するか、残りのワークロードに比例して配分できます。アプローチに関係なく、非効率による無駄を指摘し測定することが重要です。

## ショーバックとレポート作成

組織が安定したレートカードとアイドルキャパシティを処理する明確な方法を確立したら、次のステップは、それらの要素をエンジニアリングチームやプロダクトチームが実際に使用できるものに変換することです。これがショーバックの役割です。つまり、計画、説明責任、および情報に基づいた意思決定をサポートする方法で、データセンターの使用量とそれに関連するコストを可視化することです。ショーバックは、FinOpsケイパビリティの「[レポートと分析](<https://www.finops.org/framework/capabilities/reporting-analytics/>)」における主要な活動の1つです。

優れたショーバックとは、チームに課金したり、すべての資金を回収したりすることではありません。透明性を生み出すことが目的です。チームが自分たちの消費内容、コスト、およびそのコストが時間の経過とともにどのように変化するかを確認できるようになると、インフラストラクチャの統合、ワークロードパターンの調整、またはキャパシティに関するプラットフォームチームとの議論など、選択を行う能力を獲得できます。

効果的なショーバックは、生の財務データでチームを圧倒することを避けます。エンジニアは、自分たちがワークロードについて考える方法を反映した情報に最もよく反応します。たとえば、消費したvCPU時間、使用しているストレージ階層、前月と比較した使用量、異常なパターンが発生しているかどうかなどです。コストは重要ですが、コストはそれを駆動するユニットとペアになったときに最も意味を持ちます。

### ショーバックのプロのヒント：使用量、コスト、および行動の結び付け

たとえば、チームに対して月間の支出が20%増加したと示すことは、vCPU時間の消費が15%増加し、ストレージが5%増加し、彼らのクラスターに起因するアイドルキャパシティが通常の範囲から外れたと示すことよりも、はるかにアクションに結びつきにくいものです。後者は、数値が変化した理由と、それに対して何ができるかを理解するのに役立ちます。目標は、チームが論理的に考えられる方法で、使用量、コスト、および行動を結び付けることです。

ショーバックは、データセンター自体の価値を実証するための重要なメカニズムも提供します。エンジニアリングチームが、コンピューティングやストレージに対して予測可能なレートを支払っていることを確認すると、それらのサービスを提供するために何が必要であるかをより明確に理解できるようになります。これにより信頼が構築され、会話が「なぜこれが高いのか？」から「どうすればこれをより効果的に使用できるか？」や「実行しているものに対して、これは適切なサービス階層なのか？」へとシフトするのを助けます。

アイドルキャパシティの可視性もここで重要な役割を果たします。組織がアイドルコストをチームに配賦することを選択するかどうかに関わらず、ショーバックにアイドルメトリクスを含めることは、環境がどれだけうまく使用されているかについての共通の理解を生み出します。大幅なアイドルの変化に対応するエンジニアリングチームは、未使用のリソースの削減に貢献でき、リーダーシップはそのシグナルを使用してキャパシティ計画を調整できます。この可視性がなければ、スケーリング、統合、または投資に関する建設的な議論を行うことは困難です。

効果的であるために、ショーバックは一貫して、かつ既存の計画のリズムにスムーズに統合される形式で提供されるべきです。エンジニアリングチームがデータセンターの消費量を明確に把握していれば、スプリントレビュー、四半期ごとのプロダクト計画、および年次の予算編成サイクルはすべて恩恵を受けます。時間の経過とともに、ショーバックは突然のレポートや監査メカニズムではなく、チームの運用方法の一部になります。

対象読者によって、有益な詳細レベルは異なります。エンジニアリングマネージャーは、行動の傾向を強調するきめ細かい使用量情報を必要とします。プロダクトリーダーは、新たなパターンやコスト要因に注意を引くサマリーから恩恵を受けます。経営幹部のステークホルダーは、データセンターが効率的に使用されているか、アイドルキャパシティが予想範囲内にあるか、需要が予測通りに成長しているかを示す、より高レベルのビューを評価します。優れたショーバックシステムは、扱いにくくなることなく、これら3つの視点すべてをサポートします。

### ショーバックはコミュニケーションツールである

コミュニケーションツールとしてのショーバックは、社内価格設定を文脈や測定値とペアにすることで、実用的なものに変えます。それはレートカードでの選択を強化し、チームに厳格なコスト削減を強制することなく、最適化に関する議論をサポートします。最も重要なのは、プラットフォーム組織とエンジニアリング組織が同じ情報と期待値を持って運営できるようにし、データセンターをブラックボックスではなくサービスのように感じさせることです。

ショーバックはコストモデルへのヒューマンインターフェースを提供しますが、FinOpsワークフローに完全に統合するには、基礎となるデータがクラウドと同じ構造を共有している必要があります。ここでFOCUSが不可欠になります。

## データセンター向けFOCUSデータセットの生成

レートカードが確立され、消費メトリクスが定義されたら、最後のステップは、既存のFinOpsワークフローとシームレスに統合される標準化された形式でこれらのサービスを表現することです。[FOCUS仕様](<https://focus.finops.org/>)はこの構造を提供します。データセンターの使用量とコストをFOCUSで表現することにより、組織は同じ用語、同じユニット、および同じダウンストリームツールを使用して、オンプレミスのワークロードをパブリッククラウドと同じ分析およびレポートパイプラインに配置します。

パブリッククラウドを管理するFinOpsチームは、そのコストと使用量データをプロバイダーから直接取得し、[FinOpsフレームワーク](<https://finops.org/framework>)のケイパビリティである「データ取り込み」の一部として管理します。データセンターのデータの場合、組織はクラウドプロバイダーとして機能し、データ取り込み、「[レポートと分析](<https://www.finops.org/framework/capabilities/reporting-analytics/>)」、「[配賦](<https://www.finops.org/framework/capabilities/allocation/>)」、およびその他の[FinOpsケイパビリティ](<https://www.finops.org/framework/capabilities/>)のワークストリームを統合して、使用量の一元的なビューを作成する必要があります。

データセンターの使用量をFOCUSで表現することは、レポート作成を標準化する以上の効果をもたらします。これにより、経営陣はクラウド、SaaS、プラットフォーム、データセンターを含むテクノロジー資産全体を単一の分析モデルを通じて評価でき、統一された予算編成、予測、およびシナリオ計画をサポートします。

目標は、何が、いくらの社内価格で、誰によって、どの期間に消費されたかを説明する、一貫した構造化されたレコードを作成することです。レートカードが価格設定を提供し、データセンターが使用量を提供し、FOCUSがこれらを結び付ける統一された形式を提供します。FOCUSを通じて表現されると、データセンターサービスは単なるコストと消費データのもう1つのソースになり、AWS、Azure、GCP、またはSaaSプロバイダーと同じように動作します。

FOCUSマッピング戦略の確立は、すべてのステークホルダーが理解し信頼できる、明確で永続的な命名アプローチに合意することから始まります。その目的は、前提レベルで規約を設定し、データセンターで生成されたFOCUSデータセット全体で、データセンターサービス、使用量ユニット、および分類が一貫して表現されるようにすることです。これにより、FOCUSが意図した通りに機能し、集計、比較、およびレポート作成のための安定した構造が提供されます。

この戦略は、最初から適用できるほどシンプルでありながら、新しいサービスやケイパビリティが導入されたときに拡張できる十分な柔軟性を備えている必要があります。これらの決定をアドホックな選択ではなく基礎的な標準として扱うことで、組織は時間の経過とともに明確、拡張可能、かつ相互運用可能なFOCUS出力を作成できます。

以下は、このマッピング戦略を定義する際に対処すべきいくつかの重要な考慮事項です。

### サービスの命名とカテゴリ化

サービス、階層、および提供内容の命名に対する一貫したアプローチにより、データセンター環境内でコンピューティング、ストレージ、およびネットワークのレコードの比較可能性が維持されます。明確な命名規則は、同様のサービスがわずかに異なる識別子で表示されるといった偶発的な断片化を防ぎます。命名にとどまらず、マッピング戦略では、すでにクラウドデータを扱っているステークホルダーにとって馴染みのある構造にデータセンターサービスを配置するカテゴリ化モデルを定義する必要があります。

クラウド環境は、BillingAccounts、SubAccounts、Regions、AvailabilityZonesなどの階層構造を通じてリソースを整理します。データセンターはこれらの概念をネイティブには使用しませんが、類似した構造を採用することで、レポートの一貫性が大幅に向上し、データセンターのレコードをクラウドデータセットと比較しやすくなります。適切なマッピングは、データセンター環境の規模とトポロジ（Topology）によって異なります。

大規模または地理的に分散した運用では、Regionsは広範な地理的エリアを表し、AvailabilityZonesはそのエリア内の個々のデータセンターファシリティにマッピングされる場合があります。より小規模な環境では、Regionsは単に各データセンターの場所に対応し、AvailabilityZonesはその場所内の障害ドメイン、電力ドメイン、または独立したクラスターを表す場合があります。

クラウド環境では、BillingAccountは最高レベルの財務境界、つまり請求書を受け取り支出に責任を持つエンティティを表します。データセンターは請求書を生成しませんが、この概念は物理的資産の異なる部分を監督または資金提供する組織構造にきれいにマッピングされます。

企業が、異なるビジネス領域、地域、または子会社によって所有または管理されている複数のデータセンターを運営している場合、それぞれを個別のBillingAccountIdとして表現できます。これにより、組織はたとえば、企業データセンター、ローカル運用グループがサポートする地域ファシリティ、または独自のインフラストラクチャ予算を持つ子会社を区別できます。

データセンターが中央で資金提供および管理されている小規模な環境では、単一のBillingAccountIdで十分です。

SubAccountIdは、BillingAccount内の次のレベルの組織セグメンテーションを表します。技術的な構造にマッピングするのではなく、ビジネスがデータセンターのフットプリント（Footprint）に対する責任を内部的にどのように細分化しているかを反映する必要があります。これは、データセンターの使用量やコストの一部に対して説明責任を持つ部門、プロダクトグループ、サービスライン、またはその他の内部組織ユニットにマッピングされる場合があります。

BillingAccountの下に意味のある細分化がない小規模な組織では、SubAccountIdはNULLのままにすることができます。大規模な組織では、子会社がBillingAccountIdとして表示され、その内部部門がSubAccountIdとして表示される場合があります。

データセンターのコンテキストでは、HostProviderNameは物理インフラストラクチャを運営する組織または子会社を特定し、ServiceProviderNameはエンジニアリングチームが消費するコンピューティング、ストレージ、またはプラットフォームサービスを公開する内部チームまたは共有サービスを特定します。両方の役割が同じグループによって実行される場合でも、これらのフィールドを分離することでレポートの明確性が向上し、インフラストラクチャプロバイダー対サービスプロバイダーというクラウドモデルが反映されます。

これらのカテゴリ化の選択はデータセンターの運営方法を変えるものではありませんが、データセンターからのFOCUSレコードをより直感的に扱えるようにする一貫した構造的フレームワークを作成します。データセンターの概念をクラウドにインスパイアされた組織パターンに整合させることで、エンジニアリング、財務、およびFinOpsチームは、不要な運用変更を強制されることなく、馴染みのあるメンタルモデルを使用して両方の環境をナビゲートし、明確性を向上させることができます。

### タグ付けと属性特定

マッピング戦略では、チーム識別子、環境ラベル、コストセンター情報など、どの所有権またはメタデータフィールドを一貫して入力するかを定義する必要があります。可能な限り、これらのフィールドは組織の既存のクラウドのタグ付けおよび属性特定基準と一致させ、環境をまたいだレポート作成がステークホルダーにとって一貫していると感じられるようにすべきです。同時に、戦略はデータセンター内にすでに存在する属性特定構造を尊重しなければなりません。その多くはクラウドのプラクティスよりも古く、単純に置き換えることができない運用の現実を反映している場合があります。目的は均一性を強制することではなく、データセンターで生成されたFOCUSレコード全体で所有者、環境、およびサービスを一貫して特定することをサポートする、共有のベースラインを確立することです。これにより、最初から明確さが提供され、時間の経過とともに属性特定の成熟度を高めるパスが作成されます。

クラウドのタグ付けプラクティスをデータセンターの属性特定に整合させるには、多くの場合、複製ではなく変換が必要です。クラウド環境は通常、エンジニアがリソースに直接適用できる柔軟なキー・値メタデータに依存していますが、データセンターシステムはCMDB（構成管理データベース）のエントリ、命名規則、VLAN関連付け、またはプラットフォーム管理の所有権フィールドに依存している場合があります。マッピング戦略では、データセンター内の最も近い同等の属性特定シグナルを特定し、それらが要求されるFOCUSフィールドにどのように変換されるかを定義する必要があります。たとえば、CMDBのアプリケーションレコードを「Team」タグにマッピングしたり、クラスターやハイパーバイザーの命名パターンから環境の指定を導き出したりします。クラウドタグとデータセンターの属性特定を並行する真実のソースとして扱い、文書化された変換プロセスを通じてそれらを収束させることで、組織は確立された運用プラクティスを乱すことなく、統一された所有権モデルを作成できます。

### BillingPeriodStart と ChargePeriodStart

BillingPeriodStartは、データセンターの料金が累積、要約され、その後リセットされるサイクルを定義します。これは課金ウィンドウの境界を示すものであり、基礎となる使用量の粒度を示すものではありません。データセンターはクラウドプロバイダーのような方法で請求書を発行しませんが、料金やショーバックの金額をビジネスユニットに配賦する社内会計の実務は同様のパターンに従います。

エンジニアリング、財務、およびプロダクトチームがこれらを計画プロセスに組み込めるように、これらの配賦は定期的かつ予測可能なケイデンスで発生する必要があります。ほとんどの組織では、特にクラウド環境がテクノロジーのフットプリントの一部であり、そのチャージバックサイクルが期待値を設定している場合、このケイデンスはすでに月次として確立されています。

ほとんどの環境において、月次の課金期間は、クラウドの課金プラクティスと一致し、標準的なFinOpsレポートにきれいに統合され、基礎となる期間を変更することなく四半期または年次のビューに簡単にロールアップできるため、推奨される開始点であり続けます。月次サイクルを使用することで、データセンターのレコードが組織全体で消費される他のコストデータセットと自然に並ぶことも保証されます。

ChargePeriodStartとChargePeriodEndは異なる目的を果たします。これらのフィールドは、使用量が実際にいつ発生したかを示し、データセンターのテレメトリシステムが提供する解像度を反映する必要があります。一部のプラットフォームは時間単位または日単位のメータリングを提供する場合がありますが、他のプラットフォームは信頼性の高い月次集計しか提供しない場合があります。ChargePeriodフィールドは、各消費レコードの真の時間的境界を表現することで、この自然な変動を捉えます。

BillingPeriodとChargePeriodを概念的に区別しておくことが不可欠です。ChargePeriodは使用量のタイミングを表し、BillingPeriodはレポートサイクルを表します。ChargePeriodは運用の洞察、トレンド、および利用率分析をサポートするのに対し、BillingPeriodは予測可能な財務報告と「今月のコスト」という馴染みのある言語をサポートします。この分離により、誤った精度を防ぎ、レポートワークフロー全体の明確性を維持し、データセンターで生成されたFOCUSレコードの一貫性と解釈可能性を確保します。

### 使用量ユニットと測定

レートカードは、価格設定ユニット（Pricing unit）と、そのユニットの価格の両方を定義します。FOCUS消費レコードを作成する際、価格設定に使用されるユニットは、消費を表現するために使用されるユニットと直接一致する場合もあれば、異なる場合もあります。最もシンプルで明確なモデルは、PricingUnitとConsumedUnitが同じである場合（たとえば、vCPUHoursやGBMonthなど）です。これにより変換が回避され、使用量とコストの関係が理解しやすくなるためです。

しかし実際には、サービスが技術的に測定される方法が、価格設定に使用されるユニットと常に一致するとは限りません。ストレージサービスはGBあたりで価格設定されているがMBで測定されている場合や、APIサービスは1,000リクエストあたりで価格設定されているが個別の呼び出しで測定されている場合があります。これらの場合、マッピング戦略では、測定されたConsumedUnitとレートカードで定義されたPricingUnitとの間を変換するための一貫した透明性のある方法を定義する必要があります。

可能な限りユニットを一致させることが引き続き好ましいアプローチですが、戦略は測定の粒度と価格設定の粒度が異なる状況にも対応する必要があります。優先すべきは、これらのユニットの選択を一貫して適用し、コスト計算が予測可能で監査可能であり続けるように明確に文書化することです。

## データセンターからFOCUSへのマッピング

これらのマッピング決定が具体化するにつれて、データセンターでのFOCUS採用が完全な準拠から始まる必要はないことを認識することが重要です。ほとんどの組織は、不可欠なフィールドの小さなセットをマッピングすることから始め、理解が深まりデータセットが成熟するにつれて、時間をかけて拡張していきます。仕様に段階的に移行することで、マッピングモデルが自然に進化し、どのフィールドが有意義な洞察を提供し、どのフィールドが確実にデータを入力できるようになる前に追加の洗練を必要とするかが明らかになります。

この背景を念頭に置いて、次の表は、最も関連性の高いFOCUSフィールドが一般的なデータセンターのインプットに通常どのようにマッピングされるかをまとめています。マーケットプレイスの属性、外部の請求書参照、クラウド固有の予約構造など、データセンターの設定において意味を持たないフィールドは、使用をサポートする明確な目的と信頼できるデータが得られるまで、省略するか空のままにしておくことができます。

この表は、FOCUS 1.3で利用可能なフィールドをマッピングしています。詳細については、[こちら](<https://focus.finops.org/focus-specification/v1-3/>)のFOCUS 1.3仕様を参照してください。

| **FOCUSフィールド** | **説明** | **一般的なデータセンターのマッピング** |
|---|---|---|
| **Allocated*** | 社内の分割コスト配分を適用する場合にのみ使用 | クラスターレベルの配分ロジックが適用されない限り、通常はNULL |
| **AvailabilityZone** | 任意の論理グループ | 個々のデータセンターの識別子、または小規模な環境では障害ドメイン、電力ドメイン、もしくは独立したクラスター |
| **BilledCost** | 配賦されたコスト | 通常、使用量行の場合はゼロ、購入行の場合は購入価格にすることが可能 |
| **BillingAccountId / Name** | データセンター資産の所有者の識別子 | 小規模な環境では通常HostProviderNameと一致し、大規模な環境では異なる子会社（例：「Acme Asia-Pacific Infrastructure Pty Ltd」、「Acme North America Technology Operations Inc」）にマッピングされる場合がある |
| **BillingCurrency** | 社内価格設定の通貨 | 「USD」 |
| **BillingPeriodStart / End** | 課金間隔 | 月次または四半期 |
| **ChargeCategory** | 料金の分類 | 「Usage」、「Purchase」 |
| **ChargeClass** | 修正の適用を許可 | NULL、「Correction」 |
| **ChargeFrequency** | 料金が発生する頻度を示す | 「Usage-Based」 |
| **ChargePeriodStart / End** | 使用量の間隔 | 時間単位または日単位 |
| **CommitmentDiscount*** | 事前コミットメントに基づく割引の追跡に使用 | データセンター環境では通常NULL |
| **ConsumedQuantity** | 測定された使用量 | vCPU時間、GB月、GB転送量 |
| **ConsumedUnit** | 測定された消費の単位 | 「vCPUHours」、「GB」 |
| **EffectiveCost** | 調整または償却後 | 購入行の場合はゼロ、使用量行の場合は使用量に応じたレートカードによる計算コスト |
| **HostProviderName** | 物理インフラストラクチャを運営する組織または子会社 | 「Acme Asia-Pacific Infrastructure Pty Ltd」 |
