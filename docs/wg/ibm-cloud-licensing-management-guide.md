**概要:** ハイブリッド環境全体におけるコンプライアンス遵守とコスト最適化を確実にするため、ソフトウェア資産管理（SAM：Software Asset Management）とクラウド消費を同期させ、IBM Cloudライセンスの管理を改善します。このプロセスでは、一元化された可視化アプローチが必要であり、IBMのライセンス使用権（PVUやVPCメトリクスなど）とリアルタイムのクラウド利用データを紐付けることで、「二重支払い」のシナリオや監査リスクを防止します。FinOps実践者は、明確な所有権と自動化されたガバナンスエージェントを確立し、未使用のライセンスをプロアクティブに再回収（リハーベスト）して、調達を実際の需要シグナルに適合させるべきです。

このガイドは、IBM Cloudプラットフォームおよびそのサービスに関連するソフトウェアライセンスの複雑な仕組みを扱う専門家にとって、不可欠なリソースです。進化し続けるクラウドコンピューティングの環境において、ライセンスを効率的かつコンプライアンスに準拠して管理することは極めて重要です。本書を読み進めることで、基本概念から高度な戦略までを明確に理解し、実際のシナリオでベストプラクティスを導入するための十分な知識を身に付けることができます。

### 対象範囲

このガイドは特にIBM Cloudプラットフォームを対象としており、その独自のライセンス構造、課題、および機会に焦点を当てています。すでにIBM Cloudを利用している、またはビジネス運営への導入を検討している専門家向けに設計されており、ソフトウェア投資の可能性を最大限に引き出すことができます。

## IBMライセンスの理解

### 概要

本ガイドは、FinOps実践者およびITAM（IT資産管理：IT Asset Management）実践者に向けた、IBMソフトウェアライセンスに関する包括的なガイドです。初期監査からコンプライアンスチェック、継続的なモニタリングに至るまで、構造化された12週間のプロセスを提供します。IBMライセンスを理解することで、組織はクラウドおよびソフトウェアの費用を最適化し、コンプライアンスリスクを軽減し、IT資産をビジネス目標とより効果的に整合させることができます。本ガイドは、組織に多角的な利益をもたらす意思決定を支援するために設計された戦略的資産です。

### IBMライセンスを理解するためのステップ

本ガイドは、FinOpsおよびITAM実践者に対して、IBMライセンスを適切に扱うための効率的な12週間のプロセスを提示します。詳細な監査から始まり、ライセンスの分類、メトリクスの理解、コンプライアンスチェックをカバーします。目標は、リソース利用を最適化し、コンプライアンスを維持することです。部門間の連携により、強固なソフトウェア資産管理（SAM）戦略を構築します。このプロセスは、モニタリングツールのデプロイと包括的なトレーニングで締めくくられ、IBM Cloudライセンスを確実に把握できるようにします。

![](data:image/svg+xml,%3Csvg%20xmlns='http://www.w3.org/2000/svg'%20viewBox='0%200%201999%20674'%3E%3C/svg%3E)

**ステップ1：現在のIBMライセンスの監査（L1）**

  * **説明：** 既存のすべてのIBMライセンスとその条件をカタログ化する。
  * **所有者：** ITAM実践者
  * **期間：** 1週目
  * **受入基準：** すべてのIBMライセンスとその条件を網羅した詳細なリスト。
  * **アクション：** この監査にはIBM License Metric Tool（ILMT）を使用する。
  * **理由：** 重複を避け、ギャップを特定し、現在のライセンス状況を把握するため。

**ステップ2：ライセンスタイプの分類**

  * **説明：** 各ライセンスの性質を理解する。
  * **所有者：** FinOps実践者
  * **期間：** 2週目
  * **受入基準：** 永久（Perpetual）または期間（Term）に分類され、有効期限が記載されたライセンスのリスト。
  * **アクション：** スプレッドシートまたは資産管理ソフトウェアを使用する。
  * **理由：** ライセンスタイプによって、財務上およびコンプライアンス上の影響が異なるため。

**ステップ3：IBMライセンスメトリクスの確認**

  * **説明：** ライセンスメトリクスとその関連性を把握する。
  * **所有者：** FinOps実践者
  * **期間：** 3〜4週目
  * **受入基準：** UVU（User Value Unit）、PVU（Processor Value Unit）などのメトリクスと、その適用方法に関する明確な理解。
  * **アクション：** IBMの公式ドキュメントを参照する。またはIBMの専門家への相談を検討する。
  * **理由：** メトリクスの誤解による予期せぬコストや非コンプライアンスを避けるため。

**ステップ4：コンプライアンスチェック**

  * **説明：** ライセンスメトリクスおよび条件への準拠を確認する。
  * **所有者：** ITAM実践者
  * **期間：** 5週目
  * **受入基準：** すべてのライセンス条件への準拠を確認するレポート。
  * **アクション：** IBM License Metric Tool（ILMT）を使用する。
  * **理由：** 定期的なチェックにより、法的なトラブルや金銭的なペナルティを防止するため。

**ステップ5：ギャップと重複の特定**

  * **説明：** ライセンスにおける非効率性や非コンプライアンスのリスクを特定する。
  * **所有者：** FinOps実践者
  * **期間：** 6週目
  * **受入基準：** 特定されたライセンスの重複またはギャップのリスト。
  * **アクション：** スプレッドシートまたは資産管理ソフトウェアを使用する。
  * **理由：** リソースを最適化し、コンプライアンスを確保するため。

**ステップ6：SAM戦略の策定**

  * **説明：** 効果的なソフトウェア資産管理のための戦略を策定する。
  * **所有者：** 複数部門（FinOps、ITAM、法務、調達、CTO/CIO）
  * **期間：** 7〜8週目
  * **受入基準：** 導入準備が整った、文書化されたSAM戦略。
  * **アクション：** タスク追跡のためにプロジェクト管理ソフトウェアを活用する。
  * **理由：** ライセンス管理の取り組みをビジネス目標と整合させるため。

**ステップ7：モニタリングツールの導入**

  * **説明：** 継続的なライセンスモニタリングのためのツールをセットアップする。
  * **所有者：** IT運用チーム
  * **期間：** 9〜10週目
  * **受入基準：** IBMが承認したモニタリングツールの導入と微調整の完了。
  * **アクション：** IBM License Metric Tool（ILMT）およびその他の承認済みツールを使用する。
  * **理由：** プロアクティブなソフトウェア資産管理を実現するため。

**ステップ8：トレーニングとドキュメント作成**

  * **説明：** チームを教育し、プロセスを文書化する。
  * **所有者：** FinOps実践者およびITAM実践者の双方
  * **期間：** 11〜12週目
  * **受入基準：** トレーニングセッションの完了と、包括的なドキュメント一式の作成。
  * **アクション：** 社内トレーニングモジュールとドキュメントプラットフォームを使用する。
  * **理由：** 知識を共有することでミスを減らし、ドキュメント化によって将来の監査に対応しやすくするため。

### ライセンスのレビューと更新サイクル

  * **説明：** 現在のソフトウェア資産管理（SAM）戦略の有効性を評価する。
  * **所有者：** FinOps実践者およびITAM実践者の双方
  * **期間：** 四半期ごと
  * **受入基準：** SAM戦略の有効性と改善点を明確にした包括的なレビューレポート。
  * **アクション：** 四半期レポートを分析し、結果を議論するための会議を招集する。
  * **理由：** 定期的なレビューにより、変化するビジネスニーズやライセンス変更にSAM戦略を常に適合させるため。

## BYOL（ライセンス持ち込み）戦略

### 概要

組織における既存のIBM投資を最大限に活用するため、IBMは特定の条件下において、パブリッククラウドで永久ライセンスまたは期間ライセンスを使用することを認めています。IBMはこのポリシーを「適格パブリッククラウドにおけるBring Your Own Software License（BYOSL）ポリシー」と呼んでいます。[IBM Passport Advantage – Eligible Public Cloud BYOSL policy](<https://www.ibm.com/software/passportadvantage/eligible_public_cloud_BYOSL_policy.html>)

多くの組織は、永久または期間ソフトウェアライセンスを購入することで、オンプレミスのツールやアプリケーションに多額の投資を行ってきました。オンプレミスからクラウドへワークロードを移行する際、既存のライセンス使用権を活用しなければ、ソフトウェアソリューションのコストを二重に支払うことになります。ここでの目標は、有効なサポート下にあるライセンスに対してBYOLを適用し、それらのライセンスをパブリッククラウド環境へ適切に移行することで、IBMライセンス料をカバーするための追加のオンデマンド料金の支払いを避けることです。

多くの組織には、過去に購入したものの、その後廃止されたワークロード用の余剰なIBMライセンスが存在します。これらの余剰ライセンスは、クラウドコンピューティング環境で新規に作成されたワークロード向けのBYOLとして利用できる可能性があります。組織が所有し、有効なサポート下にある余剰ライセンスを使用することで、IBMライセンスをカバーするための追加のオンデマンド料金の支払いを回避できます。

### BYOLの実現可能性評価

**ステップ1：ライセンスの費用対効果の評価**

  * **説明：** BYOSLによってソリューションの費用対効果が向上するかどうかを判断する。
  * **所有者：** ITAM実践者と連携するFinOps実践者
  * **期間：** 2日間
  * **受入基準：** 現在のIBMライセンスコストと潜在的なBYOSLコストを明確に比較したレポート。
  * **アクション：** 現在のIBMライセンスコストと潜在的なBYOSLコストを比較する。

**ステップ1.1：現在のIBMライセンスコストの抽出**

  * **説明：** ソリューションの現在のライセンス費用を把握する。
  * **所有者：** FinOps実践者
  * **期間：** 3日間
  * **受入基準：** コストと使用状況レポート（CUR：Cost and Usage Report）から抽出した、現在のIBMライセンスコストの詳細な内訳。
  * **アクション：** 各クラウド（AWS、Azure、Google Cloudなど）のCURに対して、提供されたクエリを実行する。

**ステップ1.2：月次および年次のIBM Cloudライセンスコストの算出**

  * **説明：** コストを分解し、月次および年次の支出を把握する。
  * **所有者：** FinOps実践者
  * **期間：** 1日間
  * **受入基準：** 月次および年次のIBMライセンスコストレポート。
  * **アクション：** クエリ結果を使用して、月次および年次のIBMライセンスコストを算出する。

**ステップ1.3：BYOL要件の決定**

  * **説明：** ワークロードのライセンスニーズを把握する。
  * **所有者：** ITAM実践者
  * **期間：** 2日間
  * **受入基準：** 文書化されたワークロードのBYOL要件。
  * **アクション：** 具体例について、パブリッククラウドにおけるIBMの「Bring Your Own Software License」ポリシーを参照する。

**ステップ1.4：BYOLコストと利用可能性の判断**

  * **説明：** 利用可能なライセンスとサポートレベルに関する知見を得る。
  * **所有者：** ITAM実践者
  * **期間：** 1週間
  * **受入基準：** 利用可能なライセンス、サポートレベル、および関連コストに関する詳細なレポート。
  * **アクション：** IBMの有効ライセンスポジション（ELP：Effective License Position）および更新合意書／請求書を要求する。

**ステップ2：BYOLのメリット分析**

  * **説明：** BYOLの利点を理解する。
  * **所有者：** FinOps実践者およびITAM実践者
  * **期間：** 2日間
  * **受入基準：** BYOLの利用に関する費用対効果分析レポート。
  * **アクション：** 更新請求書（年次）と、年次コストに換算した時間枠／月次の使用量を比較する。

**ステップ3：ITAM実践者へのコンプライアンスアドバイスの要請**

  * **説明：** コンプライアンス要件に関する専門的な知見を得る。
  * **所有者：** FinOps実践者
  * **期間：** 1週間
  * **受入基準：** コンプライアンス要件と必要なソフトウェアの詳細なリスト。
  * **アクション：** コンプライアンスを確保するための要件とツールについて、ITAM実践者にアドバイスを求める。

**ステップ4：BYOSLのコンプライアンス評価**

  * **説明：** BYOSLを使用する際のコンプライアンス状況を把握する。
  * **所有者：** FinOps実践者およびITAM実践者
  * **期間：** 3日間
  * **受入基準：** BYOSLのコンプライアンスを維持するためのプロセスとガイドラインのリスト。
  * **アクション：** BYOSLのコンプライアンス維持に必要なプロセスを決定する。

**ステップ5：技術的実現可能性の検証**

  * **説明：** 必要なソフトウェアをクラウドにインストールできることを確認する。
  * **所有者：** エンジニアリングおよび運用チーム
  * **期間：** 1週間
  * **受入基準：** クラウド環境における、必要なソフトウェアのインストールとテストの成功。
  * **アクション：** 技術チームがクラウド環境でのソフトウェアのインストール実現可能性をテストする。

### IBM CloudでのBYOLの導入

**ステップ1：現在のライセンスの評価**

  * **説明**：クラウドへの移行前に、現在所有しているライセンスの明確なスナップショットを取得し、スムーズな移行を実現する。
  * **所有者**：ITAM実践者
  * **期間**：1週間
  * **受入基準**：条件、有効期限、および制限事項を含む、既存のすべてのソフトウェアライセンスの包括的なリスト。

**ステップ2：IBM CloudのBYOLポリシーの理解**

  * **説明**：移行時の潜在的な落とし穴を避けるため、IBM Cloud固有のBYOLガイドラインを熟知する。
  * **所有者**：FinOps実践者およびITAM実践者
  * **期間**：3日間
  * **受入基準**：IBM CloudのBYOLガイドラインと要件に関する文書化された理解、および潜在的な課題の明確化。

**ステップ3：デプロイ計画の策定**

  * **説明**：中核となるビジネスアプリケーションを優先し、依存関係を考慮した上で、IBM Cloud上にソフトウェアをデプロイするための構造化された計画を作成する。
  * **所有者**：エンジニアリングおよび運用チーム
  * **期間**：1週間
  * **受入基準**：依存関係とビジネスの優先度を考慮し、ソフトウェアのデプロイ順序を詳細に記した構造化されたデプロイ計画。

**ステップ4：本格デプロイ前のテスト**

  * **説明**：管理されたステージング環境でテストを行い、ソフトウェアがクラウド環境で正しく動作することを確認する。
  * **所有者**：エンジニアリングおよび運用チーム
  * **期間**：2週間
  * **受入基準**：ステージング環境でのテスト成功、およびすべてのソフトウェアが期待通りに動作することの確認。

**ステップ5：監視と調整**

  * **説明**：ライセンス条件への準拠を確実にするため、ソフトウェアの使用状況を継続的に監視し、ビジネスニーズの変化に応じて調整する。
  * **所有者**：FinOps実践者（クラウドコスト）、ITAM実践者（ライセンスデプロイ）、エンジニアリングおよび運用チーム（調整）
  * **期間**：継続的
  * **受入基準**：ライセンス違反の可能性に対するアラート機能を備えた、継続的な監視体制の構築。

## コンプライアンスの維持

### 監査への備え

監査通知を受け取った際、IBM License Metric Tool（ILMT）を使用しているからライセンスコンプライアンスは万全である、と思い込んでしまうことがよくあります。

残念ながら、IBMライセンスの出力データや、SAMベンダーのツール、またはSAM製品が導入されていない場合、非コンプライアンスはベンダー監査の段階になって初めて発覚することが多々あります。これにより、一部のクラウドサービスプロバイダーから、彼らが適切と考えるライセンスの購入や、過去に遡った保守料の支払いを求められ、予期せぬコストやペナルティが発生する原因となります。

### 監査に備えるためのステップ

**ステップ1：チームの編成**

  * **説明：** ライセンスの細かなニュアンス、ツールのカバー範囲、および設定を理解している専門家を集める。
  * **所有者：** プロジェクトマネージャー
  * **期間：** 1週間
  * **受入基準：** 明確な役割と責任を持つ、完全に編成されたチーム。
  * **アクション：** 社内のソフトウェア資産管理者、検出・SAMツール管理者、ILMT/HCL BigFix Inventory管理者、および関連するステークホルダーを招集する。

**ステップ2：使用権の確認**

  * **説明：** ライセンスの保有状況を把握する。
  * **所有者：** ソフトウェア資産管理者
  * **期間：** 3日間
  * **受入基準：** すべてのライセンス使用権を詳細に記載した包括的なレポート。
  * **アクション：** Passport Advantage Online（PA Online）を活用して、保有する使用権に関する知見を得る。

**ステップ3：ライセンス条件の理解**

  * **説明：** ルールを熟知する。
  * **所有者：** 法務・コンプライアンスチーム
  * **期間：** 1週間
  * **受入基準：** さまざまな合意書に基づくすべてのライセンス条件に関する、文書化された理解。
  * **アクション：** 合意書や契約書、ライセンス情報文書、およびエンタープライズ合意書を確認する。

**ステップ4：リスク領域の明確化**

  * **説明：** ライセンスにおける潜在的な問題箇所を特定する。
  * **所有者：** リスク管理チーム
  * **期間：** 4日間
  * **受入基準：** 解決策や緩和策が提示された、特定済みのリスク領域のリスト。
  * **アクション：** 既知のリスク領域、データの不正確さ、および高価値製品に焦点を当てる。

**ステップ5：必要なデータの収集**

  * **説明：** 包括的な監査に必要なデータを決定する。
  * **所有者：** ITAMチームおよびSAMツール管理者
  * **期間：** 2週間
  * **受入基準：** ハードウェアおよびソフトウェアの詳細を含む、分析準備が整ったデータセット。
  * **アクション：** SAMツール、IBM License Metric Tool、BigFix Inventory、およびその他のリソースを使用してデータを収集する。

  * **説明：** 実際の使用状況と保有する使用権を比較する。
  * **所有者：** 財務アナリスト
  * **期間：** 1週間
  * **受入基準：** 実際の使用状況と使用権との間の不一致を明らかにするレポート。
  * **アクション：** 収集したデータを使用権と照らし合わせて測定する。

## IBM Cloud Paksライセンスガイド

### 概要

Cloud Paksは、顧客のニーズを解決するソリューションを提供するIBMプログラムのスイート製品です。Cloud Paksは主にKubernetesでオーケストレーションされたコンテナプラットフォームでの使用を想定していますが、従来の仮想化環境や、両方のオプションにまたがるハイブリッド環境にもデプロイできます。

完全に柔軟なオファリングであり、各顧客はニーズに合わせて各コンポーネントプログラムの使用レベルを調整できます。ただし、Cloud Pakの使用権に対する各コンポーネントの全体的な寄与度を注意深く監視する必要があります。

## 重要用語集

  * **有効化されたプロセッサー・コア（Activated Processor Core）：** 割り当てられ、IBMプログラムで使用可能な状態にあるプロセッサー・コア。ライセンス要件を理解する上で不可欠な用語。
  * **監査（Audit）：** 顧客がIBMのライセンス条件に準拠しているかを判断するために、IBMが開始するライセンス検証活動。
  * **Bring Your Own Software License（BYOSL）：** 顧客がオンプレミスのライセンスを適格なパブリッククラウドサービスにデプロイすることを許可するIBMのポリシー。
  * **カートリッジライセンス（Cartridge Licenses）：** Cloud Pak for Dataに統合可能な、追加のオプションサービス。コンテナ環境またはスタンドアロンアプリケーションとしてデプロイ可能。
  * **コンテナ（Container）：** コード、ランタイム、システムツール、ライブラリなど、ソフトウェアの実行に必要なすべてを含む、スタンドアロンで実行可能なソフトウェアパッケージ。
  * **コンテナライセンス（Container Licensing）：** Kubernetesでオーケストレーションされたコンテナプラットフォーム上で、コンテナ化されたソフトウェアが使用する仮想CPUのみのライセンス消費量を測定する手法。コンテナライセンスの適用を受けるには、IBM License Serviceの使用が必須。
  * **デュアルデプロイメント（Dual Deployment）：** Cloud Paksをコンテナプラットフォームと従来の仮想化環境の両方にデプロイできる機能であり、導入における柔軟性を提供する。
  * **適格パブリッククラウド（EPC：Eligible Public Cloud）：** 本ページで指定されている、IBMがBYOSLポリシーの対象として適格と認めたパブリッククラウドサービス。
  * **有効ライセンスポジション（ELP：Effective License Position）：** 組織のソフトウェアライセンスのコンプライアンス状況。ELPは基本的に、現在のライセンス使用権と実際のソフトウェア消費量を照合したもの。
  * **フルキャパシティライセンス（Full-Capacity License）：** フルキャパシティライセンスでは、ソフトウェアのデプロイ方法に関わらず、サーバー内のすべての有効化されたプロセッサー・コアに対してライセンス使用権を取得する必要がある。
  * **検出ツール（Discovery Tools）：** SAMツールよりも機能が限定されたツールであり、通常、デプロイされているハードウェアおよびソフトウェアの属性を検出する。
  * **IBM Certified Containers：** プラットフォーム統合を伴うコンテナ化ソフトウェアのパッケージングおよびデプロイに関する標準基準を満たし、サポートされている任意のKubernetesオーケストレーション環境（デスクトップ、従来のITインフラ、またはクラウド）で実行可能なコンテナ。
  * **IBM Cloud Paks：** 特定のビジネスニーズに対応するために、複数のIBMプログラムを組み合わせた包括的なソリューション。Kubernetesでオーケストレーションされたプラットフォームや従来の仮想化環境へのデプロイ向けに設計されている。
  * **IBM License Metric Tool（ILMT）：** サポートされているシステム上でのライセンス割り当てサービスの管理を支援するツール。システムで使用されている製品を認識し、監視する。
  * **IBM License Service：** IBMコンテナライセンスのライセンス使用状況の追跡およびレポート作成に必要な必須ツール。
  * **IBM License Service Reporter：** 複数のKubernetesクラスターにわたるIBM License Serviceのインストール環境からライセンス数を集計するIBMのツール。IBM License Metric Tool（ILMT）のインストール環境も入力としてレポートに統合でき、コンテナ環境と従来の仮想環境の両方にわたるライセンス消費を表示できる。
  * **ライセンス比率（License Ratio）：** バンドル内の個々のプログラムごとに必要なCloud Pakライセンスの数を示す特定の比率。必要なCloud Pakライセンスの総数を計算するために不可欠。
  * **Red Hat OpenShift：** Cloud Pakライセンスに含まれる企業向けのKubernetesプラットフォームであり、コンテナオーケストレーションのための堅牢な環境を提供する。
  * **ソフトウェア資産管理（SAM）ツール（Software Asset Management Tool）：** ライセンス消費の検出、測定、記録、および使用権との照合を自動化するために使用されるアプリケーション。
  * **サブキャパシティライセンス（Sub-Capacity License）：** ソフトウェアプログラムが適格な仮想化環境にデプロイされている場合、サーバーのプロセッサー・コアの全容量未満でコアベース of ソフトウェアプログラムのライセンスを取得できる仕組み。IBMは「サブキャパシティ」を「仮想化キャパシティ」または「仮想化ライセンス」と呼ぶこともある。
  * **S&S：** ソフトウェア・サブスクリプション＆サポート（Software and Support）
  * **従来の仮想化（Traditional Virtualization）：** 現代のコンテナ化環境とは異なり、仮想マシン上でソフトウェアアプリケーションを実行する従来の手法。
  * **UVU（User Value Unit）：** 特定のソフトウェアにアクセスする許可ユーザー数を決定するためにIBMが使用するライセンスメトリクス。通常、容量ベースのライセンスよりもユーザーベースのライセンスが適しているソフトウェア製品に採用される。
  * **Kubernetes：** コンテナ化されたアプリケーションのデプロイ、スケーリング、および管理を自動化するために設計されたオープンソースプラットフォーム。コンテナのオーケストレーション層として機能する。
  * **仮想化キャパシティ（Virtualization Capacity）：** IBMプログラムがインストールされている仮想環境によって消費されるCPUコアのみのライセンス消費量を測定する手法。対照的な概念として、物理マシンまたはインフラの全処理能力に基づいてライセンス消費量を計算するフルキャパシティがある。
  * **PVU（Processor Value Unit）：** 異なるプロセッサー技術間でソフトウェアライセンスを標準化するためにIBMが導入したライセンスメトリクス。PVUは、ソフトウェアがインストールされているサーバーで使用されるプロセッサーのタイプと数に基づいて計算され、各プロセッサータイプにはIBMによって特定のPVU値が割り当てられる。
  * **仮想プロセッサー・コア（VPC：Virtual Processor Core）：** IBMプログラムに割り当てられた処理能力の量を測定するために使用される単位。ライセンスコンプライアンスにおける重要なメトリクス。

### シナリオ1：Cloud Paksと仮想化キャパシティ

**目的**

従来の仮想環境にバンドルプログラムをデプロイする際、必要なCloud Pakライセンスの数を正確に計算する。

**ステップ1：各バンドルプログラムの必要ライセンス数のカウント**

  * すべてのマシンにわたって、デプロイ予定の各バンドルプログラムに必要なライセンス数を集計する。

**ステップ2：Cloud Pak変換比率の適用**

  * 各バンドルプログラムに対して、特定のCloud Pak変換比率を適用し、必要なCloud Pakライセンス数を計算する。

**ステップ3：Cloud Pakライセンスの集計**

  * ステップ2で変換した必要ライセンス数を合算し、必要なCloud Pakライセンスの総数を算出する。

### シナリオ2：Cloud Paksとコンテナライセンス

**目的**

Kubernetesでオーケストレーションされたコンテナ環境にバンドルプログラムをデプロイする際、必要なCloud Pakライセンスの総数を正確に決定する。

**ステップ1：各バンドルプログラムの必要ライセンス数のカウント**

  * すべてのコンテナ環境にわたって、デプロイ予定の各バンドルプログラムに必要なライセンス数を集計する。

**ステップ2：Cloud Pak変換比率の適用**

  * 各バンドルプログラムに対して、特定のCloud Pak変換比率を適用し、必要なCloud Pakライセンス数を計算する。

**ステップ3：Cloud Pakライセンスの集計**

  * ステップ2で変換した必要ライセンス数を合算し、必要なCloud Pakライセンスの総数を算出する。

### シナリオ3：ハイブリッドデプロイメント – PVUライセンスとVPCライセンスの混在

**目的**

IBMプログラムの既存 of PVUライセンスを保有しており、そのプログラムがVPCメトリクスに基づくIBM Cloud Pakの一部でもある場合のライセンス要件を理解する。

**ステップ1：既存のPVUライセンスの特定**

  * IBM Cloud Pakの一部でもあるIBMプログラムについて、既存のすべてのPVUライセンスの棚卸しを行う。

**ステップ2：Cloud Pak変換比率の適用**

  * これらの各プログラムに対して、特定のCloud Pak変換比率を適用し、VPCメトリクスに基づく必要なCloud Pakライセンス数を計算する。

**ステップ3：ライセンス混在ルールの確認**

  * IT資産内でライセンス使用権を混在させることは可能ですが、単一のインスタンスをカバーするためにPVUライセンスとCloud PakのVPCライセンスの両方を同時に適用することはできない点を理解する。

**ステップ4：Cloud Pakライセンスの集計**

  * ステップ2で変換した必要ライセンス数を合算し、VPCメトリクスに基づく必要なCloud Pakライセンスの総数を算出する。

### シナリオ4：複数のCloud Paks間でのRed Hat OpenShift Container Platform（RHOCP）の共有

RHOCPは、Cloud Pak for Applications（無制限の使用権として含まれる）を除くすべてのCloud Paksに「制限付き」の使用権として含まれています。これは、このプラットフォームが特定のCloud Pak、およびそのバンドルプログラムとコンポーネントの実行をサポートするためだけにしか使用できないことを意味します。追加のRHOCPライセンスを取得しない限り、これらのRHOCP使用権を他の用途に使用することは許可されません。
