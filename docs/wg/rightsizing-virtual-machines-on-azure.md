**概要:** Azureの仮想マシン（VM）をライトサイジング（Rightsizing）するには、Azure Advisorからの推奨事項を確認し、30〜90日間のルックバック期間（Lookback period）におけるCPUとメモリのメトリクスに基づいて、十分に活用されていないリソースを特定します。アプリケーションオーナーやエンジニアと協力し、これらのVMを再構成してもワークロードのパフォーマンスに悪影響を及ぼさないこと、またベンダーの要件に違反しないことを確認します。合意（Buy-in）を得た後、サイズ変更の実行を調整し、新しい構成が本番環境で稼働する前にパフォーマンステストを確実に実施します。達成した削減額を報告し、スコープ変更による意図しないコスト増加を防ぐために、コミットメントベースの割引への影響を継続的に監視します。

このプレイブックは、FinOps、エンジニアリング、DevOpsの各チームが連携し、Microsoft Azureにおけるビジネスリスクを軽減しながら、効果的な方法でライトサイジングの推奨事項を特定・実施するためのベストプラクティスを提供します。ライトサイジングを行うことで、プロジェクトチームはプロビジョニング時にワークロードの要件に適切に一致したクラウドリソースを利用できます。

Azureが新しい機能、料金モデル、ユーザーインターフェースなどをリリースするにつれて、このような活動を実行するための具体的な手順が時間の経過とともに変化する可能性があることを認識しています。そのため、このドキュメントが長期にわたって有用であり続けるよう、可能な限りAzureが提供する関連ドキュメントへのリンクを掲載しています。本書で提供するインサイト、手順、リソースを、Azureから直接入手できる情報と組み合わせることで、FinOpsおよび使用量の最適化に関連するこのアクションについて、より完全な理解を得ることができます。

### 本プレイブックの対象読者

本プレイブックは、Azureの仮想マシンのライトサイジングによってクラウド利用を最適化することを目指す、あらゆる規模の組織のFinOps実践者、エンジニアリング、およびDevOpsチームを対象としています。

## 前提条件

本プレイブックを正常に実行するには、以下の前提条件を満たす必要があります。

  * 以下のいずれかの権限が必要です。
    * Azureサブスクリプションへの所有者（Owner）または共同作成者（Contributor）のアクセス権：推奨事項に対してアクションを実行できます。
    * 閲覧者（Reader）権限：推奨事項の閲覧のみが可能です。

さらに、Azure VMおよび関連する料金に関する一般的な理解があると役立ちます。

### 関与が必要な関係者

組織でライトサイジングを成功させるには、以下に示すペルソナ間の共同作業が必要です。

#### ペルソナ

  * **FinOps実践者（推進者）**：FinOps実践者は、十分に活用されていないVMに関するAzure Advisorの推奨事項を確認して最適化の機会を特定し、これらの結果を適切な関係者と共有します。VMの利用状況に関する詳細な分析は、ネイティブツール、自社開発ツール、またはサードパーティ製ツールを使用し、他の主要なペルソナ（アプリケーションオーナーやエンジニアなど）と対話しながら進めることで、対象のVMに最適なサイズ変更オプションを決定できます。
  * **アプリケーションオーナー（決定者）**：FinOps実践者は、特定したVMのライトサイジングによって得られるコスト削減効果と現在の利用メトリクスを、アプリケーションオーナーとエンジニアに提示します。アプリケーションオーナーとエンジニアは前提条件を検証して意思決定を行います。その際、VMの再構成がパフォーマンスに悪影響を及ぼさないこと、またワークロードに対して外部ベンダーが設定したサイズ要件を妨げないことが重要な判断基準となります。
  * **エンジニアリング（貢献者）**：エンジニアは、特定された十分に活用されていないVMのライトサイジング作業を実行し、パフォーマンスに影響がないことをテストする責任を負います。
  * **予算オーナー（共有先）**：予算オーナーは、予測されるコスト削減額について報告を受け、追加の変更が発生した場合には最新情報の共有を受けます。

#### フェーズ

  * **Informフェーズ**：
    * FinOpsチームは、ライトサイジングによる無駄の削減の価値についてエンジニアリングを教育し、ライトサイジングの最適な候補に関する必要なビジネスインテリジェンスを提供する責任を負います。
    * リーダーシップチームは、決定者として、できるだけ早い段階でFinOps活動への合意とサポートを提供する重要な役割を果たします。
  * **Optimizeフェーズ**：
    * エンジニアは、ライトサイジングが推奨されているワークロードを分析し、FinOpsチームと協力して、推奨事項がワークロードの最小要件を満たし、チームのビジネス提供に支障をきたさないことを確認します。

### 必要な情報とリソース

#### 情報

  * ライトサイジングを開始する前に、Azureの仮想マシンとその料金体系を理解することが不可欠です。
  * コミットメントベースの割引と、それがライトサイジングの意思決定に与える影響に精通していることは、落とし穴を避ける上で有益です。
  * 推奨事項の実現可能性を確認するにはリソースの所有者の意見が不可欠であるため、組織内で仮想マシンを使用している主要な所有者またはチームを特定する方法（リソースタグなど）が必要です。

#### ツール、ユーティリティ、テンプレート

ライトサイジング候補の特定は、サードパーティ製ツール、自社開発ツール、クラウドサービスやテクノロジープロバイダーから直接提供されるユーティリティなど、さまざまなFinOpsツールを使用して実行できます。これらのツールの一部は[FinOps Landscape](<https://www.finops.org/landscape/>)に掲載されています。利用可能な他のツールを特定することはできないため、本プレイブックではAzureが提供するツールに焦点を当てます。

## 本プレイブックの実行手順

### 準備と実行（30分）

  * **準備（1分）**：このステップでは、組織から提供された資格情報を使用してAzure portalにサインインします。
  * **実行（20分）**：このパートでは、分析のためにAzure portalからAzureの推奨事項にアクセスし、エクスポートします。

#### Azure Advisorの推奨事項に基づくライトサイジング

  * **Azure portal**にサインインします。
  * 「**Advisor**」に移動します。
  * 「**コスト**」ピラーの下にある「**推奨事項**」を探します。
  * 推奨事項の詳細ページに生成された推奨事項の一覧から、さらに確認したい特定の仮想マシンの使用パターンを表示できます。

これにより、対象の仮想マシンの使用率とパフォーマンスが可視化された、仮想マシンの**メトリクス**ページに移動します。デフォルトでは、メトリクス「**Percentage CPU (Avg)**」が選択され、ルックバック期間として「**過去7日間**」が設定されています。

  * 希望するルックバック期間を選択します。一般的に、30〜90日間のルックバック期間はリソース使用率の比較的正確な全体像を提供しますが、その期間が特定の状況に適しているかどうかを必ず検討してください。これは、季節的な需要によって特定の期間にワークロードがピークに達する傾向がある場合に特に重要です。選択するルックバック期間は、そのようなピークをカバーする必要があります。
  * フィルターを変更するか、他のソースを確認して、レビューに関連する他のメトリクスを調査できます。

#### ライトサイジングのためのメトリクス選択ガイドライン

**Percentage CPU (Avg) および Percentage CPU (Max)**：これらのメトリクスを組み合わせることで、CPU使用率の包括的なビューが得られ、平均負荷とピーク需要の両方が明らかになります。これは、VMが通常時およびピーク時のワークロードを処理できるか確認するために重要です。![](data:image/svg+xml,%3Csvg%20xmlns='http://www.w3.org/2000/svg'%20viewBox='0%200%20392%20206'%3E%3C/svg%3E)

**Percentage CPU (Avg)**：このメトリクスは、選択した期間における平均CPU使用率を示します。これにより、全体的なCPU使用状況を把握し、仮想マシンにワークロード用の十分なCPUリソースがあるかどうかを判断できます。平均CPU使用率が一貫して高い場合は、より多くのCPUリソースが必要であることを示している可能性があり、平均が低い場合は過剰プロビジョニング（Over-provisioning）を示唆している可能性があります。

**Percentage CPU (Max)**：このメトリクスは、選択した期間中に観測された最大CPU使用率を示します。最大パーセンテージを監視することは、ピーク使用時間を特定し、パフォーマンスを低下させることなくワークロードの一時的なスパイクをVMが処理できるか確認するために不可欠です。最大CPU使用率が頻繁に80%以上に達する場合は、レビューと潜在的なライトサイジングの兆候となります。

**Memory Usage (Avg) および Memory Usage (Max)**：これらのメトリクスは、通常時およびピーク時の条件下でVMにワークロード用の十分なメモリがあることを確認し、メモリ不足によるパフォーマンス低下を防ぐのに役立ちます。

**Memory Usage (Avg)**：このメトリクスは、仮想マシンの平均メモリ使用量を示します。このメトリクスを監視することで、パフォーマンスを低下させる原因となる頻繁なページングを発生させずに、VMがワークロードを処理するのに十分なメモリを備えているかどうかを評価できます。

**Memory Usage (Max)**：このメトリクスは、選択した期間中の最大メモリ使用量を示します。メモリ不足（Out-of-memory）の問題を防ぐために、ピーク使用時にVMに十分なメモリがあることを確認するためにこれを監視することが重要です。

**例：Disk I/O (Read/Write Ops) および Network Throughput (Bytes In/Out)**：![](data:image/svg+xml,%3Csvg%20xmlns='http://www.w3.org/2000/svg'%20viewBox='0%200%20253%20209'%3E%3C/svg%3E)これらのメトリクスは、VM of I/Oおよびネットワークの需要を理解するために重要であり、全体的なパフォーマンスとユーザーエクスペリエンスに影響を与える可能性があります。

**Disk I/O (Read/Write Ops)**：このメトリクスは、1秒あたりの読み取りおよび書き込み操作の数を追跡します。値が高い場合はディスクの使用量が多いことを示している可能性があり、VMが頻繁に高いI/O操作に達する場合は、ストレージパフォーマンスのアップグレードやディスク容量の増加を検討する必要があります。

**Network Throughput (Bytes In/Out)**：このメトリクスは、VMによって送信および受信されるデータの量を測定します。特にネットワーク通信に大きく依存するアプリケーションにおいて、ネットワーク容量がワークロードの需要に対して十分であることを確認するために、ネットワークスループットを監視することが不可欠です。

ライトサイジング用のメトリクスに関する詳細なガイダンスについては、クラウド環境におけるVMのライトサイジングのベストプラクティスと考慮事項を説明している[Microsoftのドキュメント](<https://learn.microsoft.com/en-us/answers/questions/1375053/requesting-clarification-on-azure-advisor-vm-right>)を参照してください。また、サーバーの種類に応じた以下の考慮事項にも注意してください。

**データベースサーバー**：多くの場合、高いメモリとディスクI/Oの需要があります。Memory Usage (Avg および Max) とDisk I/Oメトリクスを綿密に監視します。最大メモリ使用率が頻繁に80%以上に達する場合は、メモリの増設を検討します。

**Webサーバー**：通常、高いネットワークスループットと中程度のCPU使用率を持ちます。Network ThroughputとCPU (Avg および Max) メトリクスに焦点を当てます。最大CPU使用率が頻繁に80%以上に達する場合は、CPUの割り当てを見直します。

**アプリケーションサーバー（例：人事アプリケーションのホスティングなど）**：リソースの需要が多様な場合があります。すべてのメトリクスを監視しますが、ホストされているアプリケーションの特定のニーズ（例：大量のインメモリ処理を行うアプリケーションのメモリ使用量など）に特別な注意を払います。

  * 自身がリソースの所有者ではない場合、推奨されるサイズ変更の実現可能性について、特に日常のビジネスやコミットメントベースの割引への影響に関して、所有者に相談することをお勧めします。明確にすべき質問の例は以下の通りです。
  * VMのサイズ設定に関してベンダーからの要件はありますか？
  * 前世代のインスタンスタイプを使用していますか？
  * VM構成においてVMスケールセットを活用できますか？
  * Azure Reserved InstancesやAzure Savings Plansを使用している場合、別のVMサイズやタイプに移行する柔軟性はありますか？
  * このワークロードでバースト可能なVMを活用できますか？

サイズ変更を実行する前に、必ずリソース所有者の合意を得てください。ライトサイジングのアクションを確定する前に注意すべき他の要因については、[例外と考慮事項](<https://docs.google.com/document/d/1Tm1DE1MWgDI_2vJHGZJELUvJhz5ZVbRQ/edit#heading=h.3rdcrjn>)も参照してください。

  * ライトサイジングが関連するアプリケーションに悪影響を及ぼさないことが明確になったら、サイズ変更の実施に向けた具体的なロードマップに合意します。変更要求を実行するプロセスは組織ごとに異なります。ただし、ライトサイジング後の変更を確定して本番環境に適用する前に、社内の変更プロセスにパフォーマンステストフェーズを確実に含めることが重要です。
  * パフォーマンステストの結果がライトサイジングの推奨事項を支持しない場合、単一のリソースに対する推奨事項を却下（Dismiss）するか延期（Postpone）するかを決定する必要があります。推奨事項を却下すると、手動でアクティブにしない限り再表示されません。一方、推奨事項を延期すると、指定した期間が経過した後に推奨事項が自動的に再アクティブ化されます。
  * サイズ変更後にアプリケーションが通常通り動作すれば、ライトサイジングは成功とみなされます。FinOpsチームは、ライトサイジングの影響と、それに伴い達成された削減額を報告および追跡する責任を負います。

## 成果と成功の指標

### 本プレイブック実行による主な成果

この活動の推進者として、FinOpsチームは、推奨事項を定期的にレビューし、各リソース所有者と連携して推奨事項を実行するための実現可能性とロードマップを調整するためのコミュニケーションプロセスを定義する必要があります。ビジネスニーズは変化し続けるため、ライトサイジングは一回限りの取り組みではありません。

一般的に、ライトサイジングの頻度は組織のワークロードのピークに依存します。明確に定義されたスケジュールを用意しておくことで、管理が簡素化され、ライトサイジングの所有権と責任が明確になります。プロジェクトチームがビジネスに影響を与えることなく、過剰プロビジョニングを時間の経過とともに減少させ、良好な使用率を達成したときに、ライトサイジングの成功がもたらされます。

### 例外と考慮事項

  * 重要な注意点：FinOpsチームは、ライトサイジングの候補を特定するために必要なデータの提供をサポートします（Informフェーズ）。しかし、リソース所有者はどのデータよりも自分たちのアプリケーションの要件を熟知しているため、ライトサイジングにはリソース所有者の同意が必要です。
  * 当初はリソース所有者からの抵抗が予想されます。そのため、ビジネスケースが信頼できるデータに基づいていることを確認してください。
  * リソース所有者と一般的または予想されるスパイクについて話し合い、ビジネスの停止を避けるために、推奨されるSKUがそれらを処理できることを確認します。
  * ライトサイジングには多少のダウンタイムが伴うため、最も削減可能性が高い非本番リソースから開始するのが一般的な戦略です。リソースのタグ付け（Tagging）を行っておくことで、ビジネスに不可欠ではないリソースの特定が容易になります。
  * ライトサイジングは「全か無か」の取り組みではなく、時間をかけて段階的に進めることができます。インフラストラクチャの変更を時間をかけて小規模に実施することは、サービス中断のリスクを低減するだけでなく、社内でのライトサイジングの機運を高め、将来のライトサイジングの機会に対する合意形成を容易にします。
  * 一部のリソースがReserved Instances（RI）である可能性があることに注意してください。仮想マシンのサイズを変更すると、RIの使用率が大幅に低下する可能性があります。これにより、購入済みのRIの範囲内にある仮想マシンのコンピュート使用量に適用される割引が減少します。したがって、リソースをライトサイジングする間、既存のRIの使用率を継続的に監視することが重要です。Azureはデフォルトで[インスタンスサイズ柔軟性（ISF）](<https://learn.microsoft.com/en-us/azure/virtual-machines/reserved-vm-instance-size-flexibility>)を提供していますが、これはMicrosoftが定義するISFグループにのみ適用されることに注意してください。ISFグループ外でサイズ変更を行うと、RI料金に加えて従量課金制（PAYG）料金が発生します。そのため、RIに関連付けられているVMサイズの変更が与える影響について、RI所有者を継続的に教育することが非常に重要です。さらに、ライトサイジングが本番環境に適用された直後に、新しいVMサイズに一致するように必要なRIの交換を行えるよう、RI所有者ができるだけ早い段階でFinOpsチームをワークロードのサイズ変更に関する議論に関与させられるようなコミュニケーションプロセスを定義する必要があります。
  * 最大限のメリットを得るために、コンピュートのライトサイジングとライセンスの最適化（例：SQL Databaseインスタンスなど）を組み合わせることをお勧めします。
  * 本番リソースのライトサイジングは、変更の影響をシミュレートするための概念実証（POC）なしに実施すべきではありません。
  * リソースの最適なサイズを決定するには、過去の技術的な使用率データの分析が必要であり、CPUのみに限定すべきではありません。ただし、[メモリ](<https://learn.microsoft.com/en-us/azure/azure-monitor/agents/agents-overview>)やその他の追加メトリクスはデフォルトでは収集されないため、収集には追加の手順やツールが必要であることに注意してください。メモリメトリクスがない場合は、CPU使用率に加えて、送信ネットワーク（Outbound Network）の使用率を分析することを検討できます。
  * Azure Advisorのライトサイジング推奨事項は、過去のパフォーマンスに基づいて、アップストリーム（VMサイズを増やす場合）またはダウンストリーム（特定のインスタンスのサイズを減らす場合）のいずれかになります。
