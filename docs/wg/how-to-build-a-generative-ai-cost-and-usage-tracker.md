組織が生成AI技術の導入を進めるにつれ、関連するコストの把握と管理が極めて重要になります。このホワイトペーパーは、トークン使用量を主な測定単位として、AIワークロードにおけるコストの追跡と帰属に関する包括的なガイドを提供します。

**主要なポイント:**

  1. **トークンベースの課金**：AIサービスは通常、テキスト処理の単位であるトークンに基づいて課金します。正確なコスト見積もりには、入力トークン（プロンプト）と生成トークン（レスポンス）の違いを理解することが極めて重要です。
  2. **コスト追跡方法**：本ペーパーでは、基本的なリクエスト数のカウントから高度なトークン追跡システムまで、コスト追跡における3つの主なアプローチを説明します。各方法で、正確性と実装の複雑さのレベルが異なります。
  3. **中央集権型アプローチと分散型アプローチの比較**：組織は、中央集権的なハブ・アンド・スポークモデル、または分散型アプローチのいずれかを通じてAIコスト追跡を実装できます。それぞれ、制御、柔軟性、実装の容易さの面でメリットと課題があります。
  4. **データ管理**：包括的なトークン追跡のためのサンプルデータベーススキーマを提供し、詳細なコスト帰属と分析を可能にします。
  5. **FinOpsとの統合**：本ペーパーでは、包括的なクラウドコスト管理を実現するために、AIコスト追跡を既存のFinOpsプラクティスに統合することの重要性を強調しています。
  6. **課題と考慮事項**：モデルごとに異なるトークン化（Tokenization）戦略、潜在的な隠れたコスト、分散型の構成における正確なレポート作成の必要性など、いくつかの要因がAIコスト追跡を複雑にしています。
  7. **ベストプラクティス**：推奨事項には、AIとの対話のための標準化されたインターフェースの実装、エンジニアリングチームとの連携、組織全体での使用量に関するオープンなコミュニケーションの維持が含まれます。
  8. **プロビジョニング済みスループットの配賦**：本ホワイトペーパーでは、さまざまなユースケースにおけるプロビジョニング済みスループット（Provisioned Throughput）の使用量を配賦および追跡するための戦略を説明します。これには、共有リソース環境における使用率の最適化とコスト帰属の方法が含まれます。

本ホワイトペーパーは、AIイニシアチブに対して堅牢なコスト追跡の実装を目指すFinOps実践者（FinOps Practitioner）やITリーダー向けの基本ガイドとして機能します。これらの原則とベストプラクティスに従うことで、組織はAI支出の可視性を高め、コストを最適化し、AI投資について十分な情報に基づいた意思決定を行うことができます。

[Tokenomics Foundation](<https://www.tokeneconomics.com>)は、今後、トークンの生成、使用、価値、およびそれらに対応するすべてのコスト要因の詳細を深く掘り下げるための重要な参照先となります。FinOpsは引き続き、その価値を管理、レポートし、組織に配賦します。

## はじめに

生成AIのコスト追跡を開始する際によくある質問は、トークン使用量に関するものです。ほとんどのAIワークロードにおいて、トークンは、ビジネス内の個々のAIユースケースに容易に追跡および帰属できる唯一のコスト単位です。トークンは、入力トークンと生成トークンの2つの異なるグループに分類できます。入力トークン（AIに送信するプロンプトや指示）は通常、生成トークン（モデルが生成して応答するもの）よりも大幅に低い料金で課金されます。

トークン数の簡単な比喩は、単純な単語数カウントです。100単語のメールを1,000通生成したい場合、100,000トークンが生成されると予想できます。実際には、単語数カウントは実際のトークン数を大幅に過小評価します。トークン数は、モデルのトレーニング方法や、モデル作成者が設定したその他のさまざまなパラメータに完全に依存するためですが、このトピックは本ペーパーの対象外です。

トークンは通常、入力または生成された100万トークン（メガビットのように、Mtokensまたはメガトークン！）単位で課金されます。システムが最適化されるにつれて価格は急速に変化する傾向がありますが、本稿執筆時点では、最先端のモデルは生成された100万トークンあたり10〜20米ドルの範囲に収まる傾向があります。本番環境での使用量は、月あたり数十億トークン（ギガトークン）を容易に超える可能性があるため、コストは急速に膨らみます。これらのコストを正しく帰属させることは、長期にわたってAIワークロードの価値を評価するために極めて重要です。

AI技術の急速な台頭と普及にもかかわらず、基本的な課金単位であるトークンは、FinOpsフレームワークの確立されたプラクティスに非常によく適合します。使用量の増加はコストの増加に直結し、予測可能なパターンは事前コミットメントによって最適化でき、使用量のレポートは多くの場合リアルタイムで行われます。しかし、多くのクラウドプロバイダーやモデルプロバイダーは、コスト追跡機能ではなく、新しい機能の開発に焦点を当てています。その結果、FinOps実践者は、毎月送られてくる説明のつかない高額なAIの請求書を前に、取り残されたように感じることがあります。

コストを追跡するためのベストプラクティスにはどのようなものがあるでしょうか。それらのコストを複数のユースケースに正確に帰属させるにはどうすればよいでしょうか。現在、AIエコシステム内に存在する、困難をもたらす制限とは何でしょうか。本ペーパーでは、これらの疑問に答えることを試みます。重要な点として、ここでは主に推論（Inference）コストに焦点を当てます。データストレージ、バックアップ、負荷分散、コンテンツ配信などの他の従来のコストは、既存のFinOps資料で広くカバーされているため、対象外とします。

## 一般的なコスト状況とそれぞれの選択肢

最も基本的で不正確なAIコスト見積もり手法は、APIキーごとのリクエスト数を単純にカウントし、呼び出しごとに課金することです。これが不正確な理由は、AIエンドポイントに「こんにちは」と送信するコストと、シェイクスピアの全集を送信するコストが同じになってしまうためです（2トークン対120万トークン）。しかし、ワークロードの種類、ボリューム、請求額の規模によっては、特に困難な問題に対する迅速な解決策として、これで完全に十分な場合もあります。

正確性は向上するものの、実装の手間が増える次の手法は、トークン見積もりです。トークン見積もりは、標準的なトークン化レポートをサポートしていないモデルを使用している場合に役立ちます。トークン使用量を推定するためのさまざまなツールやコードライブラリが存在します。ただし、使用しているモデルのトークン化戦略が公開されていない限り、どのような手法で算出されたトークン数も単なる推定値にすぎず、請求額を正確に予測するために使用することはできない点に注意が必要です。

トークン見積もりには通常、各API呼び出しからの使用量（入力トークンと生成トークン）を記録する専用のデータベース（NoSQLと従来のSQLのどちらでも問題ありません）が必要です。そして、月末または請求期間の終わりに、個々のキーとユースケースに使用量を帰属させるプロセスを実行します。コストデータを収集する既存のFinOpsツールやデータベースがすでにある場合は、この情報を保存するのに適した場所になります。

最も正確な方法は、実際の入力トークン数と生成トークン数をデータベースに記録し、前述と同様のロールアップを行うことです。ほとんどのサードパーティ製モデルには、このカウント機能が標準で提供されていますが、一部のモデルではまだ提供されていません（または、まだサポートしていない古いモデルを使用している場合もあります）。

完全なトークン追跡テーブルのスキーマは、以下のようになります（[GitHub上の完全な例](<https://github.com/Barneyjm/ai_token_tracking_example/tree/main>)）：

```sql
    -- Request Keys table


    CREATE TABLE request_keys (


        request_key_id SERIAL PRIMARY KEY,


        key_name VARCHAR(255) NOT NULL,


        key_value VARCHAR(255) NOT NULL UNIQUE,


        is_active BOOLEAN DEFAULT true,


        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP


    );


    -- Model Information table


    CREATE TABLE model_information (


        model_id SERIAL PRIMARY KEY,


        model_name VARCHAR(255) NOT NULL,


        model_input_price DECIMAL(10, 6) NOT NULL,


        model_output_price DECIMAL(10, 6) NOT NULL,


        price_effective_date DATE NOT NULL,


        is_current BOOLEAN DEFAULT true


    );


    -- API Versions table


    CREATE TABLE api_versions (


        api_version_id SERIAL PRIMARY KEY,


        api_version VARCHAR(50) NOT NULL,


        release_date DATE NOT NULL


    );


    -- Token Tracking table


    CREATE TABLE token_tracking (


        tracking_id SERIAL PRIMARY KEY,


        request_id UUID NOT NULL,


        request_key_id INTEGER REFERENCES request_keys(request_key_id),


        input_token_count INTEGER NOT NULL,


        output_token_count INTEGER NOT NULL,


        model_id INTEGER REFERENCES model_information(model_id),


        api_version_id INTEGER REFERENCES api_versions(api_version_id),


        timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,


        total_cost DECIMAL(10, 6) GENERATED ALWAYS AS (


            (input_token_count * (SELECT model_input_price FROM model_information WHERE model_id = token_tracking.model_id) / 1000) +


            (output_token_count * (SELECT model_output_price FROM model_information WHERE model_id = token_tracking.model_id) / 1000)


        ) STORED


    );


    -- Index for faster querying


    CREATE INDEX idx_token_tracking_timestamp ON token_tracking(timestamp);


    CREATE INDEX idx_token_tracking_request_key_id ON token_tracking(request_key_id);


    CREATE INDEX idx_token_tracking_model_id ON token_tracking(model_id);


```

どのようなソリューションであっても、コスト見積もりの目的で、生のプロンプトや出力を長期保存することはお勧めしません。機密性の低いデータベースに機密データを保存してしまうリスクがあるためです。さらに、プロンプトと出力の保存は、システム全体のコストを増加させる要因にしかなりません。また、セキュリティ担当部門がすでにこれらのプロンプトをどこかに保存している可能性もあります。直接アクセスを依頼するか、分析に活用できる追加の列をデータストアに提供してもらうよう依頼してください。

### 中央集権型AIハブ・アンド・スポーク手法

AIケイパビリティの導入を管理および監督することを望む多くの企業は、すべてのAIワークロードが中央集権的なAIプロキシまたはハブを介してモデルと対話することを求めています。ハブが正しくセットアップされていれば、この手法によって特定のユースケースのコスト監視と管理を非常にシンプルにできます。

重要な点として、ハブへのアクセスは、特定のユースケースに直接紐づくAPIキーまたは認証キーを介して許可する必要があります。これらのキーは、他のシークレットアクセス制御メカニズムと同様に扱うべきであり、アプリケーション、ユーザー、またはユースケース間で共有してはなりません。シークレット管理のための既存の技術が存在するため、AIワークロードでもそれを活用すべきです。

しかし、中央集権的なハブでログ記録が適切に設定されていない場合、個別のAPIキーの使用状況を把握するだけでは不十分な可能性があります。中央集権的なハブの視点からは、複数のキーから高い使用量が発生しているように見えるだけだからです。入力トークンと生成トークンを個々のAPI呼び出しに帰属させることが重要です。一部の既存のFinOpsツールはこの種の使用量を処理できますが、これは成長分野であり、完全に動作するものは多くありません。さらに、モデルごとに異なるトークン化戦略を管理することは困難な場合があります。応答時に入力トークン数と生成トークン数を提供するモデルもあり、これらは直接使用すべきです。この情報を提供しないモデルについては、システムのハブ側でトークンカウントを実装する必要があります。

### 分散型AI手法

組織内でAIワークロードの導入が分散されている場合、中央集権的な手法と比較してコストの帰属特定が難しくなる可能性があります。これは、統一されたトークン見積もりやカウントのプラクティスを強制することが困難なためです。たとえば、モデルへの各APIリクエストにタグ付けを義務付けても、それを強制できない場合があります。その結果、あるユースケースがシステムのAPI呼び出しにおいて、自身の使用量を誤って帰属させてしまう（監視の目をかいくぐるために意図的に行うか、単純なミスによるものかに関わらず）ことが容易に起こり得ます。

AIの使用が分散されている場合は、エンジニアリングと連携して、各ユースケースに自動的に標準を適用できる、モデル操作用の共通インターフェース、SDK、またはその他のツールを提供することをお勧めします。負荷分散、タグ付け、その他の差別化につながらない重労働（undifferentiated heavy lifting）タスクを組み込んだInfrastructure as Code（IaC）モジュールを公開することは、推奨されるタグ付け手法の導入を加速させる優れた方法です。

このインターフェース手法と、正確なレポート作成を義務付けるAIガバナンスフレームワークを組み合わせることで、分散型アクセスにおける適切なトレードオフの仕組みを提供できます。これには、いくつかのチームにわたるAI使用量の処理に対して、より調整されたアプローチが必要となり、長期的には作業量が増える可能性があります。

これが不可能な場合は、使用量を個別のAIワークロード課金エンティティに分割することをお勧めします。AIワークロードごとに個別のサブスクリプションやアカウントを用意することで、コストが時間の経過とともにどのように変化しているかについて、より詳細なインサイトを維持できます。しかし、これはAIワークロードの長期的な保守と管理に複雑さをもたらします。

他のFinOpsケイパビリティにとって極めて重要な、基本的なタグ付けやその他のメタデータ管理技術がAIサービスやシステムに深く組み込まれるまでは、AIへの分散型アプローチにおいて、組織内のサービス利用者がオープンに議論し、誠実にレポートを作成することが求められます。

### プロビジョニング済みスループット

AIワークロードのコストを複雑にする要因として、プロビジョニング済みスループットユニット（PTU：Provisioned Throughput Units）があります。プロビジョニング済みスループットは、一部のAIサービスプロバイダーが提供する料金モデルであり、組織は固定コストで一定量の処理能力を予約できます。これにより、一貫した大量のワークロードに対して大幅なコスト削減が可能になりますが、使用量の配賦やコスト帰属の面で特有の課題も生じます。モデルは引き続きトークンを生成していますが、トークンごとの支払いは発生しなくなります。

さらに、PTUは高額になる可能性があるため、複数のユースケースで1つのPTUを共有することが一般的です。これにより、特定のユースケースにコストを配分することが困難になります。コストを分割する最も簡単な方法は、PTUの総コストを使用しているユースケースの数で割ることです。これは非常に簡単ですが、あるユースケースが他のユースケースよりもPTUを多く使用している場合、それほど消費していないユースケースにとって不公平になる可能性があります。

以下に、消費量に基づいて共有PTUコストを把握するためのアプローチの1つを示します。PTUによって実質的なトークンあたりの単価が下がるため、特定の期間に生成されたトークンの総数を集計することで、社内追跡システムでトークンあたンス価格を計算できます。このアプローチは既存のコストシステムに容易に組み込むことができますが、いくつかの軽微な複雑さも生じます。

使用率メトリクスの影響により、特定のユースケースによるトークン消費を特定のコストに結び付けることはかなり困難です。モデルプロバイダーのPTUサービスにスループットと価格設定の透明性が導入されるまでは、見積もりが最善の選択肢となります。さらに複雑なことに、モデルプロバイダーごとに異なる価格設定やPTU配分オプションがあるため、モデルプロバイダー間で「単一のPTU」と言っても、実際にはあまり意味をなしません。
