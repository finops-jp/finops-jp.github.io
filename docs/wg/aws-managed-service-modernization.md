**概要:** FinOps実践者は、AWSマネージドサービスの使用状況を分析することで、RDS、OpenSearch、ElastiCache、Redshiftなどのサービスにおけるモダナイゼーションの機会を特定できます。エンジニアリングチームと協力してワークロードをより新しいインスタンスタイプに移行し、構成を統合することで、組織は不要なクラウドコストを削減しながらパフォーマンスを向上できます。使用状況データの収集、モダナイゼーション候補の特定、およびアカウントやチーム間での進捗追跡を行うための実践的なワークフローを構築します。

この情報を活用して、アーキテクチャチームにマネージドサービス（RDS、OpenSearch、ElastiCache、Redshift）のモダナイゼーションを促します。これらのサービスは、EC2のモダナイゼーション作業に比べて再設計（Re-architecture）の負荷が低い傾向にあります。

この取り組みのメリットは以下の通りです。

  * 新しいインスタンスは通常、より安価で高速
  * マシンタイプを統合することで、十分に活用されていないコミットメント管理ツールのリスクを軽減（リザーブドインスタンス） [マネージドサービス向けのAWSリザーブドインスタンス](<https://docs.aws.amazon.com/whitepapers/latest/cost-optimization-reservation-models/reservation-models-for-other-aws-services.html>)

AWSが新しい機能、料金モデル、ユーザーインターフェースなどをリリースするにつれて、このような活動を実行するための具体的な手順は時間の経過とともに変化する可能性があります。

このドキュメントの有用性を維持するため、可能な限り関連するAWS提供のドキュメントへのリンクを掲載しています。本書で提供する知見、手順、リソースをAWSから直接入手できる情報と組み合わせることで、FinOpsおよび使用状況の最適化（Usage Optimization）に関連するこのアクションをより深く理解できます。

### 本プレイブックの対象読者

本プレイブックは、中央のFinOps実践者が以下の目的を達成するためのリソースとして機能します。

  * マネージドサービスのインスタンスタイプとリンクされたアカウント（Linked Accounts）の分布の特定
  * モダナイゼーションの機会に関するコミュニケーションの促進
  * モダナイゼーションの進捗追跡

## 前提条件

### AWSアカウントと権限

  * 適切な請求設定がされたアクティブなAWSアカウント
    * AWS Cost and Usage Report（コストと使用状況レポート）を使用してAWSマネージドサービスのモダナイゼーションを調査する際は、リソースID（Resource IDs）、時間単位の粒度、UsageType、Operation、コスト配分タグ（Cost Allocation Tags）、アベイラビリティーゾーン（Availability Zone）、リンクされたアカウント、サービス、料金オプション（Pricing Options）の属性を含めます。
    * これらの属性は、実行中のワークロードを詳細なレベルで分析し、アカウントごとのアクションを促進するために必要な粒度とコンテキストを提供します。詳細は[付録](<#appendix>)のデータ辞書を参照してください。
  * 支援や問題解決のためのAWSサポートの有効化

### **IAMロールとポリシー**

  * 最小権限のIAMロールとポリシーの実装
  * アクセスキーの定期的なローテーションとルートアカウントの使用の最小化

### 関係者

  * **FinOps実践者**は、以下のような旧世代のインスタンスに関する情報を収集します。
    * マシンタイプ、およびエンジンやノードタイプなどの特性
    * 連絡先となる、関連するリンクされたアカウントや部門

機会の範囲を特定したら、リンクされたアカウントを担当する関連エンジニアリングまたはアーキテクチャの担当者にその機会を伝えます。

FinOps実践者は、エンジニアリングの工数をかける価値があるほど重要かつ具体的な機会である場合にのみ提案を行うため、このイニシアチブを主導します。

モダナイゼーションの完了後、FinOps実践者はマネージドサービスのリザーブドインスタンスの推奨事項を確認し、ビジネスニーズと統合されたワークロードのフットプリントに基づいて購入を決定できます。

  * **エンジニアリングおよびプロダクトオーナー**は、提供された推奨事項をレビューし、インフラストラクチャのモダナイゼーションを推進するためにスケジュール設定可能なアクションを決定します。これにより、アーキテクチャの効率化とコスト削減が実現します。

## 本プレイブックの実行手順

### FinOps実践者 – 現在のマネージドサービス消費データの収集

**所要時間（見積もり）:** 30分

**担当者:** FinOpsアナリスト（FinOps Analyst）

**目的:** このステップの目的は、基本的なマネージドサービスの使用状況情報を収集することです。基本レベルの使用状況を把握することで、最適化の機会が存在するかどうかを判断できます。

**方法:** サービスを検索してAWS Cost Managementポータルに移動し、Cost Explorerを選択します。

  * AWS Cost Explorerのレポートパラメータ（インターフェースの右側にあります）を使用して、必要な情報の範囲を絞り込みます。
  * 日付範囲：複数月のデータを確認することが最適であり、まずは3ヶ月から開始することをお勧めします。3ヶ月の使用状況により、使用傾向を十分に理解し、異常値を除外できます。
    * 期間は通常、環境の変動性によって決まります。環境の変動性が高いほど、使用傾向を理解するためにより多くの過去データが必要になります。
  * 粒度：傾向をより明確に確認するには、日次の粒度が最適です。時間次の粒度はグラフが煩雑になる可能性があります。
  * ディメンション：インスタンスタイプを調査しているため、ディメンションには「インスタンスタイプ（Instance type）」を選択します。検索ボックスを使用すれば簡単に見つかります。
  * 使用タイプグループ（Usage type group）：環境に関連するコストに絞り込む必要があります。
    * RDS：「RDS: Running Hours」
    * ElastiCache：「Elasticache: Running Hours」
    * OpenSearch：「OpenSearch: Running Hours」
    * Redshift：「Redshift: Running Hours」
  * コストの集計方法を「非償却コスト（Amortized Costs）」にする：リザーブドインスタンス料金によるコストの急増を排除するため、非償却コストの使用を推奨します。
  * これにより、コストと使用時間に基づいて実行されているRDSマシンのインスタンスタイプの履歴分布を示すグラフが表示されます。
    * コストと使用状況の内訳により、実際の数値を確認でき、必要に応じてデータをCSVとしてダウンロードしてスプレッドシートにインポートできます。
  * 特定のインスタンスタイプについてさらに詳細な情報が必要な場合は、フィルターを更新して追加情報を収集できます。
    * ディメンション：「リンクされたアカウント（Linked account）」に変更します。
    * インスタンスタイプ：調査対象のインスタンスタイプでフィルターをかけます。
    * これらの修正されたフィルターにより、該当するインスタンスがリンクされたアカウントごとに分割されたグラフが表示されます。以前のグラフと同様に、実際のデータをCSV形式でダウンロードできます。

これらのマシンを実行するための現在の1時間あたりのコストを定量化するには、コストを使用量で割る必要があります。

各アカウントには、リザーブドインスタンスやその他のコスト削減要因が存在する場合があり、これによりAWSのWebページに掲載されているオンデマンド（On Demand）コストと比較して1時間あたりのコストが下がる可能性があります。

コスト削減効果を計算する際は、これらの割引をアップグレードコストにも反映させる必要があります。リザーブドインスタンスのコストとオンデマンドのコストを単純比較すべきではありません。

計算例として、R5からR6gへの移行により約10%の削減が挙げられます。料金情報と世代の選択肢は、以下のソースから収集します。

### FinOps実践者 – マネージドサービス使用状況データの分析によるエンジニアリング/プロダクト向け推奨事項の決定

**所要時間（見積もり）:** 60分

**担当者:** FinOpsアナリスト

**目的:** このステップの目的は、潜在的なモダナイゼーションの機会を特定することです。モダナイゼーションにより、スペックが向上し、多くの場合コストが低い新しいマシンを使用できるようになり、使用効率とコスト効率の両方を高めることができます。

**方法:**

**モダナイゼーション機会の特定**

モダナイゼーションの潜在的な機会を特定します。

  * データをスプレッドシートにインポートします。
  * 削減額を計算するには、以下の数式を使用します。
    * 現在のオンデマンド料金（旧インスタンス） – 新世代のオンデマンド料金（新インスタンス）
  * 差額（旧インスタンス – 新インスタンス）に、1時間あたりに実行されているインスタンスの数を掛け合わせて、対処すべき重要な機会を特定します。
  * 特定された機会領域の使用状況データをさらに掘り下げて、旧世代マシンの使用を促進している、関連するリンクされたアカウントを特定します。
  * これにより、次の段階で連絡を取るべき対象を絞り込むことができます。

**アクションが必要な項目を決定するためのしきい値**

エンジニアリングやプロダクトチームに連絡する前に、モダナイゼーションの対象となるワークロードをカバーしている既存のリザーブドインスタンスのステータスを以下のように確認します。

  * リソースがリザーブドインスタンスでカバーされているか、およびその有効期限を調査します。
  * リソースを変換した場合、リザーブドインスタンスが十分に活用されなくなる（未適用になる）のではないか：リザーブドインスタンスの利用率が低下しても移行する価値があるかというトレードオフが存在するため、慎重に評価する必要があります。
  * 最も削減可能性の高い機会を特定し、その中からモダナイゼーションの対象とするものを決定します。
  * アクションを起こす前に、作業コストとアクションのROIを理解することが重要です。例については[こちら](<#appendix>)の付録を参照してください。

**エンジニアリング/プロダクトチームへの結果の伝達**

有効な推奨事項や機会を社内の関連するステークホルダーと共有します。

  * アカウントオーナーを特定する方法は組織によって異なります。組織内の情報を収集し、モダナイゼーションの機会について話し合うための適切な連絡先を特定します。
  * メールテンプレートの例は、[こちら](<#appendix>)の付録を参照してください。
  * 調査および評価完了のスケジュールを提示します。
  * フォローアップを行い、評価と実行のスケジュールを決定します。

### 推奨事項のレビューとアクションプランの回答

**所要時間（見積もり）: 60分**

**担当者:** エンジニア / プロダクトオーナー

**目的:** 提案されたモダナイゼーションのリストをレビューし、実行（Go）または見送り（No-go）の判断に関するフィードバックを提供します。コラボレーションとアプリケーション構成の理解により、FinOps実践者はビジネスの運営方法についての理解を深めることができ、同時にエンジニアリングチームに対して既存のインフラストラクチャのレビューを促すことができます。

**方法:**

エンジニアリングおよびプロダクトオーナーは、推奨事項のリストをレビューし、以下のパラメータに基づいてフィードバックを提供します。

  * 実行可能（Actionable） – モダナイゼーションが可能であり、実行予定。変更が実施されるスケジュールを提示します。
  * 実行不可（Not actionable） – 関連するアプリケーションアーキテクチャの制約によりモダナイゼーションが不可能であり、今後の検討対象から除外します。
  * 現時点では不可（Not right now） – アーキテクチャの変更が進行中であり、現在は変更できません。FinOpsアナリストがこの推奨事項を再検討すべきスケジュールを提示します。

**コスト最適化の機会 – リザーブドインスタンスカバー率の調整**

**所要時間（見積もり）:** 30分

モダナイゼーション活動が完了したら、追加のリザーブドインスタンスを購入して、ビジネスのさらなるコスト削減を推進できます。

  * アカウント内でのリザーブドインスタンス（RI）共有ステータスを確認し、機会が最大限に活用されていることを確認します。
    * [リザーブドインスタンス共有の仕組み](<https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/ri-turn-off.html>)
    * [RI共有のメリットとデメリット](<https://aws.amazon.com/blogs/publicsector/controlling-how-your-aws-credits-and-ri-discounts-are-shared-across-your-organization/>)
  * AWSが概説するプロセスに従い、以下のようにさまざまなマネージドサービスの統合ワークロード向けにリザーブドインスタンスを購入します。
    * [RDSリザーブドインスタンスの購入方法](<https://aws.amazon.com/rds/reserved-instances/>)
    * [OpenSearchリザーブドインスタンスの購入方法](<https://docs.aws.amazon.com/opensearch-service/latest/developerguide/ri.html>)
    * [ElastiCacheリザーブドインスタンスの購入方法](<https://docs.aws.amazon.com/AmazonElastiCache/latest/mem-ug/CacheNodes.Reserved.html>)
    * [Redshiftリザーブドインスタンスの購入方法](<https://docs.aws.amazon.com/redshift/latest/mgmt/purchase-reserved-node-instance.html>)

## 成果と成功指標

### 本プレイブック実行による主な成果

  * マシンタイプを最新かつ最適なインスタンスに統合することでマネージドサービスを最適化し、アプリケーションパフォーマンスを向上
  * 最新世代のマシンは通常、実行コストが安価な傾向にあるため、オンデマンドコストを削減
  * 統合されたインスタンスタイプ環境により、リザーブドインスタンスでより積極的にカバーし、さらなる削減を推進する機会を創出

### **成功指標**

  * インスタンスタイプの統合による、より高い削減率の達成、または同等価格でのパフォーマンス向上

### **例外と考慮事項**

  * 本プレイブックでは、RDSデータベースエンジンやマルチAZ/シングルAZの選択など、モダナイゼーションの機会に影響を与える可能性のあるマネージドサービスに関連する追加のパラメータは考慮していません。
  * 新しいインスタンスファミリーは異なるCPUアーキテクチャを採用している場合があり、互換性の問題が発生する可能性があります。
  * アップグレードにより一時的にサービスにアクセスできなくなり、システム停止（Outage）につながる可能性があります。
  * インスタンスタイプの変更はパフォーマンス特性に差異をもたらす可能性があるため、慎重に監視する必要があります。
  * ストレージコストをさらに調査することで、コスト改善を図ることができます。

## 付録

### 必要な情報とリソースの例

CPUアーキテクチャの変更を伴わない、小規模な本番環境でよく使用されるRDS MySQLを例に考えてみましょう。なお、以下の料金は古くなっている可能性があり、適用される割引によって組織に適用されない場合があります。
