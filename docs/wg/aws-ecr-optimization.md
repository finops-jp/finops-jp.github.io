**概要:** FinOps実践者とエンジニアリングチームは、Amazon ECRリポジトリを分析して、サイズ超過のリポジトリ、未使用のイメージ、およびクリーンアップの機会を特定できます。リポジトリのサイズとコストのデータを収集することで、チームは古いイメージの削除やストレージフットプリントの削減などの最適化アクションの優先順位を決定できます。このガイドを、リポジトリの使用状況を調査し、エンジニアリングチームと連携して効率的なコンテナイメージ管理を維持するための実践的なワークフローとして活用してください。

Amazon Elastic Container Registry (Amazon ECR) は、AWSが完全に管理するDockerコンテナレジストリです。コンテナイメージを保存、管理、デプロイするための、安全でスケーラブルかつ効率的なプラットフォームを提供します。しかし、頻繁なアップデートや大規模な開発活動により、ECRリポジトリには多くのイメージが蓄積され、サイズとコストが増加する可能性があります。

このプレイブックは、高コストなECRリポジトリを特定し、効果的なコスト管理戦略を実装することを目的としています。リポジトリの使用状況を監視し、効率的なイメージ管理を通じてストレージを最適化し、コンテナ化されたアプリケーションデプロイにおける長期的な財務の持続可能性を維持するための、費用対効果の高いプラクティスを適用するためのガイドラインを提供します。

AWSが新しい機能、料金モデル、ユーザーインターフェースなどを導入するにつれて、このような活動を実行するための具体的な手順は時間の経過とともに変更される可能性があることを認識しています。このドキュメントが長期にわたって有用であり続けるよう、可能な限りAWSが提供する関連ドキュメントへのリンクを掲載しています。本書で提供する知見、手順、リソースを、AWSから直接提供される情報と組み合わせることで、FinOpsおよび使用量の最適化に関連するこのアクションについて、より完全な理解を得ることができます。

#### 本プレイブックの対象読者

このプレイブックは、エンジニアとFinOps実践者を対象として設計されており、FinOps実践者がエンジニアの優先すべきレジストリを特定するために活用します。具体的には、Amazon Elastic Container Registry (Amazon ECR) に関連するコストを削減する実践者を支援するために作られています。イメージのサイズを縮小するには、技術的な知識が必要となるため、エンジニアが調査と最適化活動を行う必要があります。

Amazon Elastic Container Registry (Amazon ECR) は、AWS内でのコンテナ化されたアプリケーションのデプロイと管理に不可欠です。しかし、プロアクティブに管理しない場合、コストが急増する大きな要因にもなり得ます。ECR管理におけるコスト削減は、運用コストを抑制し、クラウドデプロイの財務効率を確保するために極めて重要です。

Amazon ECRでコストを効果的に管理するには、コンテナイメージのストレージと管理を最適化するためのいくつかの戦略的アクションが必要です。コストの非効率性を早期に特定して対処するには、リポジトリのサイズと成長傾向の監視が不可欠です。これにより、組織はコストが手に負えなくなる前に、使用パターンとストレージ戦略を調整できます。

コストを抑制する最も効果的な方法の1つは、ライフサイクルポリシーを実装して、古いイメージや未使用のイメージの削除を自動化することです。このアクションにより、ストレージ要件が直接削減され、コストが低下します。必要なイメージのみを維持することで、組織はクラウド支出における一般的な非効率性である、未利用のリソースに対する支払いを回避できます。

さらに、ECRリポジトリにコスト配分タグを適用することで、さまざまな部門やプロジェクト間でコストを正確に帰属させることができます。この可視化は効果的な予算管理の鍵であり、組織は特定のイニシアチブに対するクラウド支出を追跡し、リソースの割り当てについて十分な情報に基づいた意思決定を行うことができます。また、説明責任をサポートし、ステークホルダーが自身の使用パターンの財務的影響を考慮することを促します。

圧縮や効率的なレイヤリング技術を通じてイメージストレージを最適化することも、コスト削減につながります。これらの手法は、各イメージに必要な物理スペースを削減し、ストレージコストを直接引き下げます。特に活発な開発環境においてコンテナイメージが増大する規模を考慮すると、イメージストレージにおけるわずかな効率化であっても、大幅なコスト削減につながる可能性があります。

Amazon ECRでのコスト削減を優先することは、組織のクラウドインフラストラクチャの財務健全性を維持するために不可欠です。体系的な監視、ライフサイクル管理、および最適化戦略を実装することで、組織はECRコストを大幅に削減できます。これらの取り組みは、予算超過を防ぐだけでなく、より広範な財務目標とも一致し、クラウド技術への投資が最大の価値をもたらすことを保証します。

## 前提条件

このプレイブックを実行するには、情報を収集するためのリポジトリの記述（Describe）権限、およびレイヤーの削除（Delete layer）/ ライフサイクルポリシーの更新（Update Lifecycle Policy）権限を持つ、AWS [**Amazon Elastic Container Registry (ECR)**](<https://aws.amazon.com/ecr/>) に対する十分な権限を持つAWSアカウントへのアクセスが必要です（ECRレジストリの数に応じて、マスター一括請求アカウント、専用のECRレジストリアカウントがある場合はそのアカウント、または特定のアカウントのみで実行できます）。

ECRの場合、以下のIAM権限が必要です。

  * ecr:DescribeRepositories
  * ecr:DeleteRepository
  * ecr:PutLifecyclePolicy

#### 関与が必要な関係者

  * FinOps実践者またはエンジニア：リポジトリ情報を収集し、決定者であるエンジニアまたはアカウント所有者が、収集されたデータに基づいて情報に基づいたアクションを実行できるようにします。
  * エンジニアまたはアカウント所有者：未使用のECRリポジトリを特定できるため、推進者（Driver）となります。
  * エンジニアまたはアカウント所有者：決定者（Decider）として、リポジトリの削除やライフサイクルポリシーのアップロードに必要なアクションを実行します。

## プレイブックの実行手順

以下の手順を完了して、ECRのコストと使用状況を分析および最適化します。環境によっては、これを毎年繰り返すことが有益な場合があります。

#### リポジトリ情報の収集 – 10分

目的は、アカウントまたは組織内の各リポジトリに関する情報を収集し、現在の状態やデータに基づいて次のステップに関する意思決定を行うことです。リポジトリ名、サイズ、および概算コストを収集します。データ収集は、ECRリポジトリを持つアカウントへのアクセス権を持つ人であれば誰でも実行できます。

  * [**スクリプトのダウンロード**](<https://github.com/s4mur4i/finops_scripts/tree/main/aws_ecr>)：提供されたダウンロードリンクをクリックしてスクリプトファイルを取得します。通常、このファイルはUnix/Linuxベースのシステムでは拡張子が「.sh」、Windowsシステムでは「.bat」になります。
  * **コマンドラインインターフェース（CLI）を開く：**
    * Windowsの場合：Win + Rキーを押し、「cmd」または「PowerShell」と入力してEnterキーを押します。
    * Macの場合：Spotlightを開き（Cmd + Spaceキーを押す）、「ターミナル」と入力してEnterキーを押します。
    * Linuxの場合：キーボードショートカットのCtrl + Alt + Tキーを使用してターミナルを開きます。

**スクリプトが保存されているディレクトリに移動する：** cdコマンドに続けて、スクリプトが保存されているディレクトリへのパスを入力します。例：  
bash scriptname.sh

**スクリプトの実行**：CLIでスクリプトを実行するコマンドを入力します。具体的なコマンドは、スクリプトの名前と拡張子によって異なります。Unix/Linuxベースのシステムの場合、以下のようになります。  
bash scriptname.sh

「.bat」ファイルを使用するWindowsシステムの場合、以下のようになります。  
scriptname.bat

スクリプトの実行が完了したら、CLIに表示された出力を確認します。以下のような出力が表示されます。
[code] 
    # ./ecr_repository_sizes_osx.sh

    Repositories,Size,Expected Cost

    statsd-exporter,7 MB,0

    lambda-cloudfront-partition,394 MB,.03

    cloudflare_watcher,34 MB,0

    root-account-usage-notifier,225 MB,.02

    k8s-metadata-injector,20454 MB,1.99

    ...


[/code]

#### スプレッドシートへのデータアップロードと分析 – 5分

  * 目的は、クリーンアップが必要なリポジトリを特定し、削減可能性に基づいて優先順位を決定することです。分析のためのガイドラインは以下の通りです。
  * コスト分析：リポジトリをコスト順に並べ替えることで、最も高価なリポジトリを特定できます。調査のクイックリファレンスとして、最初はコスト上位10個に焦点を当て、結果が出たら次のバッチに進むか、中央値の価格を計算して中央値以上のすべてを調査します。コストを削減するために、イメージ数またはイメージサイズを削減できます。具体的な実行方法はステップ3と4を参照してください。
  * サイズ分析：リポジトリをサイズ順に並べ替えることで、最適化が必要なイメージを特定できます。アプリケーション所有者と協力して、サイズを削減する（よりスリムなイメージを使用するか、イメージから不要なコンポーネントを削除する）、またはライフサイクルルールを使用して、廃止された/不要なイメージを自動的に削除します。
  * 冗長性の特定：リポジトリを確認することで、廃止されたリポジトリや冗長なリポジトリを特定できます。
  * 実行可能な洞察（Actionable Insights）：上記のガイドラインを使用して、次のステップに向けたアクションプランを策定できます。

#### ライフサイクルポリシーのデプロイ – 30分

将来的に未使用のイメージが自動的にクリーンアップされるように、ライフサイクルポリシーをデプロイすることがベストプラクティスです。([ECRのベストプラクティス](<https://github.com/awslabs/aws-config-rules/blob/master/aws-config-conformance-packs/Security-Best-Practices-for-ECR.yaml>))

以下を基本ポリシーとして使用し、組織の要件に合わせて調整できます。ライフサイクルポリシーを実装する前に、安全のために既存のポリシーを必ずバックアップしてください。提供されたYAMLを出発点として利用し、組織の特定のニーズに合わせてカスタマイズします（詳細については、エンジニアリングチームに相談してください）。詳細については、[イメージのクリーンアップの自動化](<https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html>)に関するAWSドキュメントを参照してください。

要件の変化に応じて、定期的にポリシーを見直し、修正します。
[code] 
    {

    "rules": [

    {

     "rulePriority": 1,

     "description": "Clean untagged",

     "selection": {

       "tagStatus": "untagged",

       "countType": "imageCountMoreThan",

       "countNumber": 1

     },

     "action": {

       "type": "expire"

     }

    },

    {

     "rulePriority": 2,

     "description": "KeepLatest",

     "selection": {

       "tagStatus": "tagged",

       "tagPrefixList": [

         "latest"

       ],

       "countType": "imageCountMoreThan",

       "countNumber": 1

     },

     "action": {

       "type": "expire"

     }

    },

    {

     "rulePriority": 3,

     "description": "Keep 9 versions",

     "selection": {

       "tagStatus": "tagged",

       "tagPrefixList": [

         "v"

       ],

       "countType": "imageCountMoreThan",

       "countNumber": 9

     },

     "action": {

       "type": "expire"

     }

    },

    {

     "rulePriority": 4,

     "description": "Keep 20 images all together",

     "selection": {

       "tagStatus": "any",

       "countType": "imageCountMoreThan",

       "countNumber": 20

     },

     "action": {

       "type": "expire"

     }

    }

    ]

    }


[/code]

タグなし（Untagged）または宙ぶらりん（Dangling）のイメージは、使用されていない場合は安全に削除できます（Dockerイメージはレイヤーで構成されています。宙ぶらりんまたはタグなしのイメージは、どのタグ付きイメージとも関係のないレイヤーです。これらは使用されておらず、安全に削除できます）。

`Latest` はDockerにおける特別なタグであり、通常は保持することがベストプラクティスですが、本番環境では使用しないことが推奨されます。

**現場のFinOps（FinOps In The Wild）：** あるFinOpsチームは、本番環境にデプロイされるゴールデンイメージにセマンティックバージョニングを使用し、ロールバックを可能にするために9つのイメージを保持しています。また、潜在的な開発用イメージや特別なイメージに対応するために、グローバルで少なくとも20のイメージを維持しています。この構成は、イメージを効果的に管理するための推奨アプローチの1つです。  
---  

#### イメージサイズの削減 – 20分

ライフサイクルポリシーを設定した場合でも、単一のイメージにデバッグシンボルや不要なリソース/アプリケーションがDockerコンテナ内にインストールされている場合があります。可能な限り最小のイメージを使用することをお勧めします。Devops Cubeは、[Dockerイメージサイズを削減する方法](<https://devopscube.com/reduce-docker-image-size/>)についていくつかの提案を提供しています。

#### レポーティングと監視 – 30分

アクションを実行した後、請求やコストと使用状況レポート（CUR）への変更がすぐには反映されない場合があることに注意してください。通常、初期の影響は2日以内に明らかになります。この期間中は、請求データを監視し、過去の記録と比較することが不可欠です。

レポーティングは、成功を伝え、改善を理解するために重要です。監視は、リソース内の変化を検出するために重要です。考慮すべき主なポイントは以下の通りです。

  * **反映の遅延：** 請求やCURレポートにおける即時の変更は、最適化を即座に反映しない場合があります。そのため、短期間で実際の影響を観察するには耐性が必要です。

  * **監視期間：** 実行したアクションがコストとリソース使用率に与える初期の影響を測定するために、少なくとも2日間の監視期間を推奨します。

  * **過去のデータとの比較：** 更新された請求およびCURレポートを定期的に過去のデータと比較し、実行したアクションによって達成された最適化とコスト削減の効果を評価します。

  * **ステークホルダーとのコミュニケーション：** 改善とコスト削減が定量化され、データによって実証されたら、その成果を組織やステークホルダーに伝えます。透明性のあるアップデートを提供することで、目標との整合性を確保し、最適化の取り組みの成功を示すことができます。

## 成果と成功の指標

このプレイブックを使用することで、ECRコストを削減し、将来のコストが制御不能に陥るのを防ぐことができます。

#### 本プレイブック実行による主な成果

  1. **予測可能なコスト：** ECRリポジトリのコストがより予測可能かつ管理可能になり、リソース使用の最適化により予算管理が向上します。
  2. **予算への影響の緩和：** 各リポジトリに制限を設けることで、サイズが増加した場合でも請求全体への影響を最小限に抑え、コスト管理を強化できます。
  3. **リソース利用の最適化：** プレイブックはリソース使用を最適化し、リポジトリサイズを組織のニーズに合わせることで、不要な支出を削減します。
  4. **コスト予測可能性の向上：** 組織はECRコストの予測可能性向上を実感でき、財務計画とリソース割り当ての改善が容易になります。
  5. **請求管理の向上：** リポジトリを制限内に収めることで、組織は請求を効果的に管理し、予期しないコストの急増を防ぐことができます。

#### 例外と考慮事項

  1. **コンプライアンス要件：** リポジトリサイズの調整がコンプライアンスや規制の要件に違反しないようにしてください。コンプライアンスへの配慮とコスト最適化の取り組みのバランスを取る必要があります。
  2. **データ保持ポリシー：** 一部のリポジトリには特定のデータ保持ポリシーが適用されている場合があります。意図しないデータ損失を避けるため、リポジトリサイズを最適化する際はこれらのポリシーに留意してください。

**コラボレーションとコミュニケーション：** 開発、運用、および財務チーム間のコラボレーションが不可欠です。効果的なコミュニケーションにより、コスト最適化の目標と運用要件との整合性が確保され、サイズ調整中の衝突を回避できます。
